🔧 First on-robot run · read before the workshop

Bring-up & test plan — from a powered-off robot to a driving one.

Ordered by risk, lowest first. Every test says exactly what to do (input) and what to watch in AdvantageScope (output), plus pass/fail and the fix if it fails. This is the "prove each class works on the real robot" pass.

!Safety rules — non-negotiable

  • One hand on the Driver Station Enter (disable) key for every first-motion test.
  • First setpoints are tiny. A mechanism that moves the wrong way at full effort breaks things.
  • Bring up one mechanism at a time. Use Test mode (§3) — it isolates them.
  • Nobody's hands in a mechanism's path while it's enabled.
  • If the dashboard shows a red config-verify or disconnect Alert, stop and fix it before enabling.
  • The safety net (soft limits, current limits, verified config) is a backup — never the plan.

0Pre-power — Phoenix Tuner X

Before the code runs, prove the hardware is sane. All of this is in Tuner X, robot powered but disabled.

  • Device inventory. Every device from the hardware map answers: swerve drive 10/20/30/40, steer 12/22/32/42, CANcoders 11/21/31/41, Pigeon 2, and subsystem motors 30/31/32/42/34 (shooter), 10/34/13 (intake), 20/33 (transport). A missing device = wrong id, bad wiring, or unpowered.
  • Licenses. Every TalonFX shows Pro + seasonal licensed (we default to FOC eventually; even VOLTAGE needs the seasonal).
  • Firmware current and matched across devices.
  • Two buses. Swerve devices are on SwerveCANivore; subsystem motors on the RIO bus. IDs repeat across buses (10 exists on both) — that's fine.
  • CANcoder magnet health "green" on all steer encoders (you'll need their offsets in §7).
  • Battery ≥ 12.5 V resting. A weak battery skews everything, especially SysId.
💡 Benchtop-only work?

Constants.DISABLE_SWERVE = true stops the teleop drive command; useful when the drivetrain isn't on the cart. (There's a DISABLE_SUBSYSTEMS flag too, but Test mode is the cleaner isolation — §3.)

1Deploy & first boot

  1. Green build: ./gradlew build. Never deploy red.
  2. Deploy: ./gradlew deploy — jar + the deploy/ folder (PathPlanner paths) go to the RIO.
  3. Open AdvantageScope → File ▸ Connect to Robot (roboRIO address). You should see the NT tree populate.
  4. Read the dashboard before enabling. Expect: zero config-verify alerts, zero disconnect alerts, an alliance set, an auto selected.
TEST 1 — clean boot
INPUT
Deploy, do not enable yet.
WATCH
Dashboard Alerts widget · DS console.
PASS
No Device config … FAILED alert, no … motor disconnected alert. DS console shows the DogLog/Signal-Logger start lines (§2).
FAIL
A config-verify alert names a device → that device didn't accept its config (§12). A disconnect alert names a device → CAN/power to it. Fix in Tuner X before continuing.

2Telemetry & the data log — prove logging works first

Everything below depends on reading values in AdvantageScope, so verify the pipes before the mechanisms. This exercises Telemetry, DogLog, the WPILib DataLog, Phoenix SignalLogger, SignalHub, FaultReporter, and LoopTimer.

TEST 2a — DogLog + the .wpilog data log are running
INPUT
Boot the robot; watch the DS console, then briefly enable teleop.
WATCH
Console for [DogLog] LogThread started and DataLog: Logging to '…/logs/FRC_*.wpilog' and [phoenix] Signal Logger Started. In AdvantageScope, the NT:/… tree fills with mechanism keys.
PASS
All three log lines appear; the .wpilog file exists on the RIO and grows; keys like Shooter/Hood/PositionRotations are live.
FAIL
No DataLog line → Telemetry.init(...) not called in the Robot constructor. No keys in NT → you're at competition mode (Telemetry.init(true,…) disables NT publish; use false at the workshop) or not connected to the right address.
💡 Data log vs NT

DogLog always writes the DataLog (.wpilog on the RIO — pull it post-session, it's the source of truth). It also publishes to NetworkTables live when not in competition mode. Phoenix SignalLogger writes the high-rate .hoot separately — that's what SysId reads. AdvantageScope opens all three.

TEST 2b — loop & CAN health
INPUT
Enable teleop, let it idle ~10 s.
WATCH
Robot/LoopOverruns, Robot/MaxLoopMs, CAN/RioUtilizationPercent.
PASS
LoopOverruns stays 0 (or barely climbs at startup then stops); MaxLoopMs < 20; CAN utilization comfortably under 90%.
FAIL
Overruns climbing → something blocking on the loop (§12 troubleshooting). CAN > 90% → too many signals; confirm SignalHub.optimizeAll() ran (it's in the Robot constructor).
TEST 2c — disconnect detection actually fires
INPUT
Disabled, briefly unplug one non-critical motor's CAN (or power), watch, replug.
WATCH
Its <name>/Connected key and the dashboard.
PASS
Within ~0.5 s: Connected → false and a "… motor disconnected" Alert appears; both clear on replug.
FAIL
No alert → the device never registered (only excalib2 Motors self-register). Confirms your telemetry safety net for the rest of the day.

3The Test-mode bring-up harness

Enter Test + Enable in the Driver Station. This cancels teleop/auto wiring and activates the bring-up controls (gated to Test mode, so they can never fire while driving). Mechanisms sit idle until you command them — perfect isolation.

Control (primary controller, Test mode only)Does
L1 (hold)Coast the whole robot — swerve + intake four-bar + turret — so you can back-drive/zero by hand.
D-pad ▲ / ▼SysId quasistatic forward / reverse on the mechanism under test.
D-pad ▶ / ◀SysId dynamic forward / reverse on the mechanism under test.
△ / ✕ (hold)Intake to OPEN / CLOSE — quick direction & range check.
◯ (hold)Flywheel at a low fixed 10 rot/s — direction & readiness check.
💡 Choosing the "mechanism under test"

The D-pad SysId targets one mechanism, set in RobotContainer.configureTestBindings():
var mut = superstructure.shooter.hood; and var mutSubsystem = superstructure.shooter;
Change those two lines and redeploy to characterize the turret, flywheel, four-bar, drum, etc. For the FOC pass, swap the four sysIdQuasistatic/Dynamic calls for the …Torque variants (§11).

4Per-mechanism bring-up recipe

Run this four-step loop for each articulated mechanism, in Test mode, before ever running the superstructure. It proves feedback, direction, range, and control — in that order, safest first.

  1. Zero-check the feedback. Hold L1 (coast), move the mechanism by hand to a known pose, release. Watch <name>/PositionRotations. Because the intake/hood/turret aren't fused CANcoders yet, they're boot-seeded — so the reported position is only right if the robot booted in the seeded pose. Confirm the number matches reality; if not, the boot seed (or ratio) is off.
  2. Direction check (tiny). Command a small motion (for intake use △/✕; for others, a small setpoint via the harness or a temporary binding). Watch that positive command → the geometrically-positive direction. Wrong way? flip .inverted(...) in the config — never negate setpoints.
  3. Range / soft limits. Command toward each end. It should stop at the soft limits, not the hard stop. Watch <name>/PositionRotations plateau at the configured min/max and <name>/StatorAmps stay low (not pinned against a stop).
  4. Closed-loop tracking. Command a mid-range setpoint. Overlay <name>/GoalRotations (or GoalRPS) vs <name>/PositionRotations (or VelocityRPS). They should converge; <name>/AtGoal (or AtSpeed) flips true. Ringing/overshoot → note it for the SysId session (§11).
⚠️ Two-motor mechanisms: watch current on the direction check

The four-bar and flywheel each have a follower. If they were configured with the wrong opposed flag, the direction check shows high StatorAmps and little/no motion — the motors are fighting. Fix the follower flag before anything else.

6Rollers & game-piece detection

TEST 6 — intake roller direction & current-spike
INPUT
Test mode: hold △ (intake OPEN also spins the roller). Then feed a real game piece into the intake.
WATCH
Intake/Roller/OutputVolts (direction/sign), Intake/Roller/StatorAmps (baseline vs jammed).
PASS
Roller pulls the piece in (not out). When a piece seats/stalls, StatorAmps jumps clearly above the free-spin baseline.
FAIL
Spins out → flip roller .inverted(...). Spike buried in noise → note the free-spin vs jammed amps to tune roller.currentSpike(threshold, debounce) thresholds later.
💡 Tuning currentSpike from this test

Read the two current levels off the log: set the threshold between them, and set the debounce just past the start-up inrush spike (~0.1–0.3 s). The transport drum/belt aren't roller-type but verify their direction the same way via their /VelocityRPS sign.

7Swerve — the riskiest bring-up, do it carefully

🚫 Why this gets its own careful section

SwerveConfig was hand-derived from the old library and is not yet robot-verified: module inversions, CANcoder offsets, and the coupling ratio. A wrong steer offset makes a module point 90° off and the robot lurches on first enable. Verify offsets and directions on blocks before the wheels touch the ground.

7.1 · Steer offsets & angle sanity (robot on blocks)

  1. Hand-align all four modules so the wheels point dead-ahead (use a straightedge across each pair).
  2. In Tuner X, read each steer CANcoder's absolute position at this aligned pose → these are your offsets. Put them in SwerveConfig (the module constants' magnet offset). Redeploy.
  3. Verify: disabled, watch Swerve/ModuleStates — with wheels hand-aligned forward, all four reported angles read ~0. Rotate one module 90° by hand → its state reads ~90°. If a module reads the negative of what you turn, its CANcoder direction is inverted.

7.2 · Drive & steer direction (still on blocks)

TEST 7 — module directions
INPUT
Teleop (blocks!), DISABLE_SWERVE=false. Push the left stick gently forward.
WATCH
All four wheels spin forward (top of wheel moves toward robot front) and stay pointed ahead. Swerve/ModuleTargets vs Swerve/ModuleStates converge.
PASS
All wheels drive forward together, modules hold ~0°. Rotating the stick spins the robot the expected way.
FAIL
A wheel drives backward → that drive motor's inversion. A module snaps 180° off → steer inversion or a bad offset. Fix in SwerveConfig, redeploy, re-verify.

7.3 · On the ground — slow drive, heading, odometry

  • Slow field-centric drive. Teleop caps are cautious (2 m/s / 1.5 rad/s in SwerveConfig) — leave them for the first drive. Stick forward = robot moves away from you.
  • Operator perspective: set alliance to Red in the DS — "forward" should still be away from the driver station (CTRE flips it). Then Blue.
  • Odometry sanity: drive a known 1 m; Swerve/Pose should advance ~1 m in the right axis. Spin 360°; heading returns to start.
  • resetHeadingCommand() re-zeros field-forward if the robot's notion of forward drifts.
💡 Odometry period as a health read

Swerve/OdometryPeriodSeconds should hover near 0.004 s (the 250 Hz thread). A large or jumpy value means CANivore trouble.

8Vision — Limelight MegaTag2

TEST 8 — pose fusion
INPUT
Point the turret camera at AprilTags. Drive slowly near known tags.
WATCH
Swerve/Vision/TagCount, Swerve/Vision/Rejected, Swerve/Vision/Pose, and whether Swerve/Pose snaps toward truth when tags appear.
PASS
TagCount ≥ 1 with tags in view; Rejected false when still; Swerve/Pose corrects toward the tag-based estimate. Spinning fast → Rejected true (the isFast gate working).
FAIL
Nothing → wrong limelight NT name (must be "limelight-turret") or the MegaTag2 orientation feed isn't reaching it. Pose jumps wrong → the turret-offset heading feed or turretPoseToRobotPose transform is off (the camera rides the turret).
⚠️ Turret angle must be trustworthy first

Vision depends on the turret's reported angle (it's fed as the camera platform heading). Bring up the turret (§5) and confirm its position reads correctly before trusting vision.

9State machines & superstructure goals

With each mechanism proven in isolation, test the coordination. Back to teleop.

TEST 9 — goal fan-out
INPUT
Teleop. Trigger a goal — the superstructure buttons are R2 (intake), □ (shift-activate), ○ (delivery). (Zone triggers are stubbed on, so button + face buttons drive the goal.)
WATCH
Superstructure/State, then Intake/State, Shooter/State, Transport/State — they should switch together to match the goal's tuple.
PASS
Requesting a RobotState flips all three subsystem states to the goal's tuple; the mechanisms move accordingly; Superstructure/RobotAtState goes true when they arrive.
FAIL
A subsystem doesn't switch → check its …/LastDenied (illegal transition) or …/Pending (a guard blocking it, e.g. transport waiting on shooter-ready). The state machine logs the reason.
💡 Readiness chain

Shooter/Ready = turret aligned ∧ flywheel atSpeed ∧ hood adjusted. Transport only feeds when the shooter is ready — so if the drum/belt "won't run" in a shoot goal, check Shooter/Ready first; it's gating them by design.

10Autonomous

  1. Dry-run on blocks: pick an auto in the chooser, enable Autonomous with wheels off the ground. Watch Swerve/Pose trace the path in AdvantageScope's field and the named commands fire (Superstructure/State changes at the right waypoints).
  2. Confirm named commands act. If the robot follows the path but never intakes/shoots, a named command isn't registered → a silent no-op. Check the DS console for PathPlanner warnings; every name in the .auto must be in registerCommands().
  3. On the ground: a short, simple auto first, hand on disable.

11SysId → FOC session

Once everything moves correctly, characterize for real gains and (optionally, per mechanism) switch to FOC. Full procedure in the manual — this is the on-robot flow using the harness.

  1. Point the harness at the mechanism: set mut/mutSubsystem in configureTestBindings(), redeploy.
  2. Test mode, run all four D-pad routines (▲▼ quasistatic, ▶◀ dynamic), each until the mechanism reaches a soft limit or steady speed — release at the limit. Data goes to the .hoot automatically.
  3. Analyze the hoot in AdvantageScope's SysId tool → kS, kV, kA (+kG). Put them in the subsystem's Gains; set kP modest, raise to crisp, add kD if it rings.
  4. FOC (per mechanism, optional): in configureTestBindings() swap the four routines for the …Torque variants, redeploy, re-run — those gains are amps. Then in the config: .controlMode(TORQUE_CURRENT_FOC) and drop in the amp gains. Treat the first enable after the switch like a new mechanism.
⚠️ Don't restructure the shooter maps

The distance→angle/RPS/time-of-flight interpolation tables are competition-proven. Tune by adjusting points, never by rewriting the code.
