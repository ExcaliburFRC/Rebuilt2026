3Concepts & architecture BASICS

Everything in this library follows five ideas. Internalize these and every API in Parts II–IX will feel inevitable.

  1. The control loop runs on the motor, not the RIO. Your code picks a setpoint; the TalonFX closes the loop onboard at 1 kHz. The RIO never computes a PID. This is why control is smooth and why loop timing on the RIO barely matters for control quality.
  2. Everything is in mechanism units. The device is configured with its gear ratio, so it natively reports and accepts mechanism position — radians of hood, meters of elevator. Encoder ticks and conversion factors do not exist in robot code. A whole category of unit bugs is gone.
  3. Declare, don't write. A mechanism is a MechanismConfig (pure data) handed to an archetype (Positional / Linear / Velocity / Roller). The archetype supplies control, telemetry, alerts, SysId, and simulation. Your subsystem file is declarations + coordination — never plumbing.
  4. Config is a verified contract. Every device configuration is applied, read back, field-compared, and retried up to 5×; failure raises a dashboard Alert. A half-configured motor is never silent.
  5. State is a declared table. Subsystem modes live in a StateMachine with explicit, guarded, default-deny transitions. Illegal sequences aren't runtime bugs — they're unrepresentable.
🧠 DEEP The one asterisk: VOLTAGE today, FOC tomorrow

All migrated mechanisms run ControlMode.VOLTAGE because their gains were ported from v1's voltage-based software PID (mathematically equivalent, now onboard at 1 kHz). TorqueCurrentFOC — the library's default and end-state — needs amp-based gains from a SysId session; they are different numbers, not a conversion. The switch is one field per mechanism (§6, §35). Treat VOLTAGE as "correct today", FOC as "the tuned upgrade".

4Robot boot & the loop BASICS

Two places wire the library into the robot's lifecycle: the constructor (once) and robotPeriodic (every 20 ms). The order is load-bearing.

frc/robot/Robot.java — the exact wiring
public Robot() {
    Telemetry.init(false, null);                 // §27 — start DogLog + SignalLogger (false = not competition)
    AllianceFlip.configure(FIELD_LENGTH_METERS, FIELD_WIDTH_METERS);   // §31 — season field dims

    robotContainer = new RobotContainer();       // constructs all subsystems (device configs apply HERE)

    SignalHub.optimizeAll();                     // §12 — AFTER all devices exist: disable unused CAN signals
}

@Override public void robotPeriodic() {
    LoopTimer.start();                           // §30

    SignalHub.refreshAll();                      // §12 — fresh signals BEFORE commands run
    FaultReporter.poll();                        // §29 — 1 Hz device-fault scan (skips itself in sim)

    ShiftUtil.update();                          // game-specific (hub shifts)
    robotContainer.periodic();
    CommandScheduler.getInstance().run();        // subsystem periodics + all commands

    LoopTimer.end();
}
🧠 DEEP Why refresh-before-scheduler is free performance

Status signals are CAN frames cached on the RIO. If you refresh after the scheduler (v1 did), every command that reads position/velocity is reading last loop's frame — a built-in 20 ms of sensor latency on top of everything else. Refreshing first costs nothing and removes it. This single ordering decision is measurable in tuning.

⚠️ Why optimizeAll() must come last in the constructor

SignalHub.optimizeAll() tells every registered device to stop sending CAN frames for signals nobody registered — a big bus-utilization win. But it must run after every device exists: a device constructed later would have its signals silenced before it registered them. Constructor order: telemetry → subsystems → optimize.

5CANDeviceId — id + bus, inseparable

A tiny value type that prevents a classic wiring bug: right id, wrong bus.

API + examples
new CANDeviceId(30);                       // device 30 on the RIO bus ("")
new CANDeviceId(11, "SwerveCANivore");     // device 11 on the CANivore

id.id();          // the numeric id
id.busName();     // the bus name
id.toCANBus();    // a Phoenix CANBus object
id.toString();    // rio[30]  or  SwerveCANivore[11]  — used in alerts/logs
🧠 Why a whole type for two fields?

Because an id alone is ambiguous — both our buses have a device 10. Every constructor in the library takes a CANDeviceId, so the bus travels with the id and can never be forgotten or mismatched. (Pattern credit: Team 254.)

🚫 Gains never cross modes

A kP of 60 V/rot and a kP of 60 A/rot are wildly different physical stiffnesses. Changing controlMode without re-deriving gains (SysId, §35) is the classic way to make a mechanism violent. This is why every config carries a comment like // FOC after SysId.

🧠 DEEP All requests are pre-allocated

Motor constructs every request object once and mutates it per call (withPosition(...)) — zero garbage on the hot path, which matters at 50 Hz on the RIO. You get this for free; just don't create your own request objects per loop if you ever drop to the device layer.

8MotionConstraints — the motion profile

Shapes how a mechanism approaches its setpoint. Runs onboard as MotionMagic. All units are mechanism units (rot/s, rot/s² — or m/s, m/s² for LinearExtension).

the two constructors
new MotionConstraints(cruiseVel, accel, jerk)   // 3 args → TRAPEZOIDAL profile
new MotionConstraints(expoKV, expoKA)            // 2 args → EXPONENTIAL (MotionMagicExpo)
new MotionConstraints(expoKV, expoKA).withCruiseCap(maxVel)   // Expo with a speed ceiling
?How should it approach the setpoint?
DEFAULT
2-arg Expo
Shaped by the motor's own kV/kA (always volts, even under FOC). Time-optimal, smooth at both ends, nothing to hand-tune. Pick this for positional moves. Starters: expoKV ≈ 12 / free-speed-in-mech-units, expoKA ≈ 0.1–0.5 (higher = softer stop).
FIXED SPEED
3-arg trapezoidal
A known, constant cruise speed: mechanisms that must move in lock-step, or a hard velocity cap that came from a mechanical/safety spec (the intake four-bar's 1.5 rad/s is exactly this).
NONE
omit .motion(...)
Setpoint applied directly. Right for flywheels (velocity steps are fine); wrong for any position move with real inertia.
🧠 DEEP How the two-vs-three-arg overload works, and MotionMagicVelocity

The 3-arg form fills MotionMagicCruiseVelocity/Acceleration/Jerk; the 2-arg form fills MotionMagicExpo_kV/_kA and flags Expo. For a VelocityMechanism, a nonzero accel (or Expo) makes setpoints run through MotionMagicVelocity — a jerk-limited velocity ramp — instead of a raw velocity step. Jerk = 0 disables jerk limiting (fine for most mechanisms).

11DeviceConfigs — apply · verify · retry DEEP

Why a config problem on this robot is an Alert on the dashboard instead of a mystery at the match.

API
DeviceConfigs.applyVerified("Shooter/Hood", talonFX, configuration)   // → boolean success
DeviceConfigs.applyVerified("Hood/CANcoder", cancoder, configuration)
DeviceConfigs.retry("name", () -> someCtreCall())                      // retry any StatusCode call ≤5×

What applyVerified actually does, in order:

  1. Apply the full configuration with a 100 ms timeout, retrying up to 5× on any non-OK status (boot-time CAN hiccups are real, not hypothetical).
  2. Read back the device's entire configuration.
  3. Compare the serialized configs token-by-token, numeric tokens with a 10⁻³ tolerance (the device stores some values in fixed point — exact equality would false-alarm).
  4. On failure: raise a persistent Alert ("Device config verify FAILED: name") and log a DogLog fault. The boolean return lets callers gate readiness.
🧠 Why verification matters

A brownout or CAN glitch mid-apply can leave a device with half its config — wrong soft limits, no current cap. Without read-back, nothing tells you until the mechanism misbehaves. With it, the failure is loud at boot, when it's cheap. (Pattern credit: 254/3061.)

All device telemetry (position, velocity, current…) arrives as CAN "status signals". SignalHub decides how often each is sent and refreshes them all in one batch per loop.

⚠️ The swerve does NOT go through SignalHub

CTRE's SwerveDrivetrain runs its own 250 Hz odometry thread with time-synced CANivore reads — it manages its own signals. Don't register swerve devices here; you'd fight it.

🧠 Why batching matters

Refreshing N signals individually = N blocking CAN transactions scattered through the loop. Refreshing them as one batch per bus = one wait, all values coherent from the same instant, and predictable loop time. It also makes "is this data fresh?" a single well-defined moment in the loop (§4).

13.1 · Constructor — name and the leader motor

new MechanismConfig(String name, CANDeviceId motorId)

name is the telemetry path. Every value the mechanism logs (Name/PositionRotations, Name/GoalRotations, Name/AppliedVolts, Name/SupplyAmps, Name/StatorAmps, Name/TempCelsius, Name/Connected, Name/AtGoal…) appears under it in AdvantageScope, and it names the config-verify and disconnect Alerts. Convention: "Subsystem/Mechanism". motorId is the leader TalonFX. What breaks without care: a lazy name makes logs unsearchable; there's no other cost.

13.2 · .follower(CANDeviceId, boolean opposed)

Default: none. Adds a second motor on the same shaft. It receives the same verified configuration and a hardware Follower request — no second control loop, no RIO involvement, and it disappears from your code entirely.

🧠 opposed is a physical fact, not a choice

Two motors mounted mirror-image spin opposite directions to produce the same mechanism motion → opposed = true. Same orientation → false. Get it wrong and the motors fight: huge current, no motion, hot motors. If bring-up shows exactly that, flip this flag first.

13.3 · .controlMode(ControlMode)

Default: TORQUE_CURRENT_FOC. See §6 for the full decision. Sim always forces VOLTAGE regardless of what you set here. Breaks without care: switching this field without re-deriving gains — the gain units change from volts to amps, so old numbers become a violently wrong stiffness (§6, §35).

13.4 · .inverted(boolean clockwisePositive) and .neutralMode(NeutralModeValue)

Defaults: counter-clockwise-positive; Brake. Inversion defines which physical direction is "positive" — set it so positive = the direction that makes geometric sense (arm up, elevator up, intake out). Neutral mode is what the motor does at zero output: Brake resists motion (hold position-ish), Coast spins free.

?Brake or Coast?
BRAKE
Elevators, anything that must not fall on disable, drive motors.
COAST
Mechanisms you hand-position in the pit (four-bar, turret, hood) and flywheels (let them spin down).
The intake four-bar is Coast for exactly this reason — see §21.

13.5 · .gains(Gains real, Gains sim)

Default: all-zero (the mechanism will not close a loop — a valid state only for rollers). Maps to the device's Slot0Configs. Full field reference in §7; gravity type decision:

13.6 · .motion(MotionConstraints)

Default: none (setpoints applied directly). Maps to MotionMagicConfigs. Full treatment in §8. For a positional mechanism with no motion constraints, goals go through the plain position closed loop — legitimate for very light mechanisms, harsh for anything with inertia.

13.7 · .currentBudget(CurrentBudget)

Default: new CurrentBudget(40, 30) — a deliberately conservative floor so an unconfigured mechanism can't cook itself. Maps to CurrentLimitsConfigs + TorqueCurrentConfigs. Full treatment in §9.

13.8 · Feedback: .rotorToMechanismRatio(double) or .fusedCANcoder(...)

?Is there an absolute encoder (CANcoder) on the mechanism?
YES
.fusedCANcoder(new CANDeviceId(encId), rotorToSensorRatio, sensorToMechanismRatio, Rotations.of(magnetOffset)) (+ .cancoderDirection(...) if needed)
FusedCANcoder: the device blends the absolute sensor with the rotor — drift-free, survives power cycles, no boot homing. The library configures the CANcoder itself (magnet offset, direction) verified, before the motor references it. On real hardware only; sim falls back to rotor feedback automatically.
NO
.rotorToMechanismRatio(r) — rotor rotations per mechanism unit
Relative feedback. You must seed position at boot: mechanism.resetPosition(...) from a known pose or a homing routine. Forget the seed and every angle is offset by wherever the rotor woke up.
⚠️ The three ratios, precisely

rotorToSensorRatio = rotor turns per CANcoder turn (gearing between motor and sensor). sensorToMechanismRatio = CANcoder turns per mechanism turn (1.0 when the sensor is on the output shaft). rotorToMechanismRatio = rotor turns per mechanism unit — for LinearExtension, that's rotor turns per meter. Mixing these up produces "moves ~14× too far" bugs; if motion is wildly scaled, audit the ratio first.

13.9 · .softLimits(Angle rev, Angle fwd) / .softLimitsMeters(Distance, Distance)

Default: none. Two layers of protection: goals are clamped before being commanded (archetype), and SoftwareLimitSwitchConfigs is set on the device so even a bug can't drive past (device). Breaks without it: a bad setpoint slams the mechanism into its hard stop at full current.

13.10 · .continuousWrap()

Default: off. For turrets: goals are wrapped to the nearest equivalent angle (mod one rotation) inside the soft-limit range — shortest legal path, never unwinding the cable loop. Requires softLimits. The wrap math: take the target mod 1 rotation nearest to the current position; if it falls outside the limits, shift by a full rotation back inside; clamp.

13.11 · .tolerance(Angle) / .toleranceMeters(Distance)

Default: 0.02 rotations. The "reached" window that drives atGoal/atSpeed triggers. Tune it against the mechanism's real noise floor: too tight → the trigger never fires and the superstructure waits forever; too loose → "ready" fires before the mechanism truly is (the shooter fires early). For a velocity mechanism the same number is read as rot/s.

13.12 · .peakVoltage(double fwd, double rev)

Default: ±12 V. A hard output ceiling in voltage terms — an independent second clamp on top of the motion profile. Use for mechanisms whose speed was validated at a specific voltage (the intake four-bar ships ±1.5 V, preserving its v1 behavior exactly).

13.13 · .ramps(double openLoopSeconds, double closedLoopSeconds)

Default: 0 (no ramp). Seconds from zero to full output. Use open-loop ramps to soften duty-cycle rollers that snap belts; closed-loop ramps sparingly (they fight the profile — prefer MotionConstraints for shaping).

13.14 · Sim models: .simRotationalModel / .simArmModel / .simElevatorModel / .simModel

Default: none — and then the mechanism does not move in simulation (logic runs, physics doesn't). Full model reference in §19. The generic .simModel(factory) is the escape hatch for custom physics.

✅ The minimum viable config per archetype

Roller: name + id + currentBudget + sim model. Velocity: those + gains + tolerance (+ ratio). Positional/Linear: those + feedback ratio (or fused CANcoder) + motion + softLimits. Everything else is refinement.

🧠 whileIn vs onEnter — the decision that matters most

onEnter fires once. whileIn schedules a Command that runs the entire time and is cancelled at exit. Use onEnter when a single call sticks (MotionMagic goal — the device keeps chasing it). Use whileIn when something must be maintained every loop (a roller's duty cycle, a tracking goal that follows a moving target, a timed oscillation). The intake uses whileIn for all three states because the roller output needs continuous commanding.

🧠 whileIn commands and requirements

Build them with the subsystem's run(...)/runEnd(...) factories so they require the subsystem. That integrates with the scheduler: a manual command on the same subsystem interrupts the state's command cleanly, and vice versa. A bare Command with no requirement would fight other commands invisibly.

⚠️ Startup semantics

The initial state's onEnter/whileIn fire on the machine's first periodic() or first request() — not at construction. Declare everything first; the first tick starts it. (This is why you can build the machine as a field and chain declarations safely.)

🚫 Pitfalls

① Forgetting machine.periodic() → pending requests never retry, no state telemetry. ② Reusing one Command object as whileIn for two states — each state needs its own instance. ③ Guards with side effects — keep them pure reads. ④ Using forceState as a normal transition — it skips your safety table.

Intake.java — the real file
public class Intake extends SubsystemBase {

    private final PositionalMechanism fourBar = new PositionalMechanism(
            new MechanismConfig("Intake/FourBar", new CANDeviceId(LEFT_FOUR_BAR_MOTOR_ID))
                    .follower(new CANDeviceId(RIGHT_FOUR_BAR_MOTOR_ID), true)   // mirror-mounted → opposed
                    .controlMode(ControlMode.VOLTAGE)      // ported v1 volt gains; FOC after SysId
                    .rotorToMechanismRatio(GEARING)        // 14.14 rotor turns per four-bar turn
                    .gains(FOUR_BAR_GAINS, FOUR_BAR_SIM_GAINS)   // kP=4π V/rot (v1's 2 V/rad), kG=0.8 Arm_Cosine
                    .motion(FOUR_BAR_MOTION)               // trapezoid @ 1.5 rad/s — v1's velocity clamp
                    .softLimits(Radians.of(INTAKE_MIN_ANGLE_RAD), Radians.of(INTAKE_MAX_ANGLE_RAD))
                    .peakVoltage(FOUR_BAR_PEAK_VOLTS, -FOUR_BAR_PEAK_VOLTS)     // ±1.5 V — v1's 2nd clamp
                    .currentBudget(FOUR_BAR_BUDGET)
                    .tolerance(Radians.of(INTAKE_ANGLE_TOLERANCE_RAD))
                    .neutralMode(Coast)                    // hand-positionable in the pit
                    .simArmModel(DCMotor.getKrakenX60Foc(2), GEARING, 0.3, 0.3,
                            INTAKE_MIN_ANGLE_RAD, INTAKE_MAX_ANGLE_RAD, START_ANGLE_RAD));

    private final RollerMechanism roller = new RollerMechanism(
            new MechanismConfig("Intake/Roller", new CANDeviceId(ROLLER_MOTOR_ID))
                    .controlMode(ControlMode.VOLTAGE)
                    .currentBudget(ROLLER_BUDGET)
                    .simRotationalModel(DCMotor.getKrakenX60Foc(1), 0.002, 3.0));

    private final StateMachine<IntakeStates> machine;
    public final Trigger atPositionTrigger;

    public Intake() {
        fourBar.resetPosition(Radians.of(START_ANGLE_RAD));   // no fused CANcoder yet → boot seed

        machine = new StateMachine<>("Intake", CLOSE)
                .whileIn(OPEN,  run(() -> { fourBar.setGoal(Radians.of(OPEN.angle));  roller.runDutyCycle(OPEN.voltage); }))
                .whileIn(CLOSE, run(() -> { fourBar.setGoal(Radians.of(CLOSE.angle)); roller.runDutyCycle(CLOSE.voltage); }))
                .whileIn(PUMP,  pumpCommand())
                .transitionFromAny(OPEN).transitionFromAny(CLOSE).transitionFromAny(PUMP);
                // ^ every move legal — intentional: this mechanism has no unsafe orderings

        atPositionTrigger = new Trigger(() -> Math.abs(
                machine.getCurrentState().angle - fourBar.getPosition().in(Radians)) < INTAKE_ANGLE_TOLERANCE_RAD);
    }

    private Command pumpCommand() {                            // shake pieces in: oscillate + feed
        return Commands.repeatingSequence(
                run(() -> { fourBar.setGoal(Radians.of(PUMP_HIGH_ANGLE_RAD)); roller.runDutyCycle(PUMP.voltage); }).withTimeout(PUMP_PERIOD_SECONDS),
                run(() -> { fourBar.setGoal(Radians.of(PUMP_LOW_ANGLE_RAD));  roller.runDutyCycle(PUMP.voltage); }).withTimeout(PUMP_PERIOD_SECONDS))
            .withName("Intake Pump");
    }

    public Command setStateCommand(IntakeStates s) { return machine.requestCommand(s); }  // buttons/autos
    public void requestState(IntakeStates s)       { machine.request(s); }                // superstructure fan-out
    public Command coastCommand()                  { return fourBar.coastCommand(this); } // pit crew

    @Override public void periodic() { fourBar.periodic(); roller.periodic(); machine.periodic(); }
}

21.2 · Why the roller is only four lines

A roller is open-loop: it holds no position and no speed, it just spins. So there are no gains (nothing to close), no motion profile (nothing to shape), no soft limits (free spinning), no tolerance (no target). What it still gets from those four lines: a verified config, batched signals, DogLog telemetry, a debounced disconnect Alert, a sim model — and currentSpike() on demand. Less config because there is genuinely less to decide, not because it's second-class.

21.3 · The constructor — seeding, then the machine

🧠 fourBar.resetPosition(Radians.of(START_ANGLE_RAD)) — the magic-number seed

No fused CANcoder yet (§13.8), so the four-bar's position is relative: at power-on it only knows "zero is wherever I woke up." The robot always boots stowed, so we declare "you are at the stow angle." The constant π − 0.732601 − 0.159 is the empirically measured stow angle carried over from v1 — left un-collapsed so the calibration history stays legible. Skip this line and every angle the mechanism ever reports is offset by the boot pose. When the CANcoder gets fused (offset calibration pending), this line and the constant disappear.

🧠 Why whileIn for all three states, not onEnter

onEnter fires once; whileIn schedules a command that runs the entire time and is cancelled at exit. The four-bar goal alone could be a one-shot (MotionMagic keeps chasing it onboard), but the roller duty-cycle must be commanded continuously — so each state's behavior is a whileIn that does both, every loop. One consistent pattern instead of a mixed one.

🧠 Why run(…) and not a bare lambda

run(…) is SubsystemBase.run: it builds a RunCommand that requires this subsystem. The requirement is the point — it means a manual intake command interrupts the state's command cleanly through the scheduler, and two things can never drive the roller at once. A plain Runnable would have no requirement and no scheduling semantics.

🧠 Why transitionFromAny on every state

The intake has no unsafe orderings — CLOSE→PUMP, OPEN→CLOSE, anything goes. Declaring transitionFromAny for all three states says that explicitly. In a default-deny machine, freedom must be declared just like restriction — so when a reader sees this, they know "all moves legal" was a decision, not an omission. A mechanism with real interlocks (say, "never extend while climbing") would instead list only its legal edges and let everything else be denied.

🧠 atPositionTrigger — one trigger, correct in every state

It compares the four-bar's angle to machine.getCurrentState().angle — the current state's target — not to a fixed constant. So the same trigger answers "is the intake where its current mode wants it?" in CLOSE, OPEN, and PUMP alike. The superstructure consumes it as a readiness gate.

21.4 · The pump command — composition as the timing engine

PUMP physically shakes pieces in: the four-bar oscillates 1.6 rad ↔ 0 rad every half-second while the roller keeps feeding (v1 behavior, preserved). Look at what is not in the implementation: no timers, no counters, no "phase" flag, no cleanup code. repeatingSequence(high.withTimeout(0.5), low.withTimeout(0.5)) — the command framework does the timing, the alternation, and (because it's a whileIn) the instant cancellation when the state changes. This is the house style: express time-structured behavior as command composition, never as hand-rolled state.

35SysId & tuning — concept, code, and the FOC path

SysId replaces gain-guessing with measurement. This section covers what it measures, exactly what the library's routines do in code, how to run and analyze a session, and — separately — how to characterize for TorqueCurrentFOC, whose gains are amps-based and need their own routines.

35.1 · What SysId measures, and how

The routine drives the mechanism with two stimulus shapes while recording position, velocity, and output:

TestStimulusWhat it reveals
QuasistaticA slow output ramp (acceleration ≈ 0)kS (the output where motion starts) and kV (the output-vs-velocity slope)
DynamicAn output step (constant output)kA (how much output acceleration costs)

Each is run forward and reverse — four runs total per mechanism. The analyzer fits output = kS·sign(v) + kV·v + kA·a to the data (plus kG for gravity mechanisms) and hands you the feedforward set; you add feedback (kP/kD) by hand afterwards (§7's symptom table).

35.2 · The code — what the routines actually are DEEP

Every mechanism carries two lazily-built WPILib SysIdRoutines. The voltage routine (for ControlMode.VOLTAGE gains) is, inside the library:

inside Mechanism — the voltage routine (you don't write this; know what it does)
new SysIdRoutine(
    new SysIdRoutine.Config(
        null,                 // ramp rate: null → WPILib default, 1 V/s (quasistatic)
        Volts.of(4),          // step size: 4 V (dynamic)
        null,                 // timeout: null → default 10 s safety cutoff
        state -> SignalLogger.writeString(config.name + "/SysIdState", state.toString())),
    new SysIdRoutine.Mechanism(
        (Voltage volts) -> motor.setVolts(volts.in(Volts)),   // the drive callback
        null,                 // no WPILib log callback — Phoenix records instead (below)
        subsystem));          // requirement → interruptible like any command
🧠 The three things worth understanding in that snippet

① The state string is the synchronization key. Each loop, the routine writes its test state (quasistatic-forward, dynamic-reverse, none…) into the hoot via SignalLogger. The analyzer uses this channel to slice the log into the four runs — it's how "which samples belong to which test" is known.

② The device is the data logger. We pass null for WPILib's per-loop log callback on purpose: the TalonFX's own position/velocity/voltage/current signals are already streaming into the hoot at device rate, which is better data than 50 Hz RIO sampling. The routine only needs to drive and label.

③ It's just a Command. quasistatic(direction) / dynamic(direction) return Commands that require the subsystem — so they bind to buttons, are interruptible by disable, and can't fight your other commands.

35.3 · Running a session

  1. Bench-prep. Mechanism free over its full travel; soft limits verified (they're your run-stopper); battery fresh (a sagging battery skews voltage data); someone's hand on the disable key.
  2. Deploy with the bindings, enable teleop, and run each of the four tests: hold the button, let the mechanism sweep until it reaches a soft limit or steady speed, release. Release at the limit — samples pushed against a stop are garbage the analyzer must not see.
  3. Between runs, return the mechanism near the opposite end so each run gets full travel.
  4. Grab the hoot. Phoenix wrote everything to the RIO (or the CANivore's USB drive if attached). Pull it via Tuner X or AdvantageScope's log download.

35.4 · Analyzing

  1. Open the hoot in AdvantageScope → the SysId tool (or CTRE Tuner X's analyzer).
  2. Map the fields: test state = <Name>/SysIdState · position/velocity = the device's Position/Velocity signals · applied output = MotorVoltage (or TorqueCurrent for §35.5).
  3. Read the fit: it yields kS, kV, kA (and kG if you select the arm/elevator mechanism type — it separates gravity from friction using the forward/reverse asymmetry). Sanity-check the fit quality (r²) before trusting numbers.
  4. Fill the constants: put them in the subsystem's Gains; start kP modest, raise until tracking is crisp, add kD if it rings (§7). Update the MotionConstraints if the measured free speed says your profile was optimistic.

35.5 · FOC-wise — torque-current characterization

🚫 Why you cannot reuse the voltage results

Voltage SysId answers "volts per unit of speed/accel". FOC closed loops output amps of torque current — a different physical quantity, and the relationship between them shifts with battery state (that immunity is FOC's whole appeal). So FOC needs its own characterization that drives amps, not volts.

The wrinkle: WPILib's SysId API is volts-typed — there is no amps overload. The standard CTRE idiom (which the library implements for you) is to reinterpret the routine's "volts" as amps:

inside Mechanism — the torque routine (the volts-as-amps idiom)
new SysIdRoutine(
    new SysIdRoutine.Config(
        Volts.of(5).per(Second),   // read as: 5 AMPS per second quasistatic ramp
        Volts.of(20),              // read as: a 20 AMP dynamic step
        null,
        state -> SignalLogger.writeString(config.name + "/SysIdTorqueState", state.toString())),
    new SysIdRoutine.Mechanism(
        (Voltage amps) -> motor.forceAmps(amps.in(Volts)),   // "volts" driven as TorqueCurrentFOC amps
        null, subsystem));

You call it exactly like the voltage pair — same binding pattern, different methods:

torque-current characterization bindings
controller.povUp().whileTrue(shooter.hoodSysIdQuasistaticTorque(SysIdRoutine.Direction.kForward));
controller.povDown().whileTrue(shooter.hoodSysIdQuasistaticTorque(SysIdRoutine.Direction.kReverse));
controller.povRight().whileTrue(shooter.hoodSysIdDynamicTorque(SysIdRoutine.Direction.kForward));
controller.povLeft().whileTrue(shooter.hoodSysIdDynamicTorque(SysIdRoutine.Direction.kReverse));
🧠 The details that make this work

① It runs while the mechanism is still in VOLTAGE mode. The drive callback uses Motor.forceAmps(…), which applies a TorqueCurrentFOC request regardless of the configured control mode — so you characterize before the switch, breaking the chicken-and-egg. (Regular setAmps deliberately refuses outside FOC mode; forceAmps is the characterization exception.)

② The output is clamped by your CurrentBudget's torque peaks (§9) — the 20 A step can't exceed what you declared safe.

③ In the analyzer, select TorqueCurrent as the "voltage" channel and state = <Name>/SysIdTorqueState. The resulting "volt" gains are amp gains — no conversion, drop them straight in.

④ Real hardware only. Torque-current isn't meaningfully simulated; run this on the robot.

Then complete the switch — two edits in the subsystem's constants/config:

.controlMode(ControlMode.TORQUE_CURRENT_FOC)     // was VOLTAGE
.gains(HOOD_GAINS_FOC, SIM_GAINS)                // sim set unchanged — sim always runs VOLTAGE
// keep .withTorquePeaks(...) on the CurrentBudget — it's the output clamp in FOC (§9)

First enable after the switch: treat it like a new mechanism (§36) — small setpoints, hand on disable. Expect crisper tracking and identical behavior at 12.6 V and 11.2 V; that's the point.

⚠️ MotionMagicExpo's kV/kA stay in volts

Even in FOC mode, the profile-shaping MotionConstraints Expo kV/kA are always volt-referenced (a Phoenix convention — they describe the motor, not the loop). Only the Gains change units at the switch.

💡 The drivetrain

swerve.sysIdTranslation / sysIdSteer are the voltage routines (CTRE's stock SysId requests). Torque-current drive characterization for the swerve needs a custom request applying TorqueCurrentFOC per module — a flagged follow-up; until then, drive modules switch to FOC using Tuner X's swerve tuning flow.

35.6 · After SysId — the polish loop

  1. Feedback by symptom — §7's table: kP up to crisp, kD against ringing, kI almost never.
  2. Live-polish with TunableNumber (§28) for setpoint-shaped values (shooter RPM points, tolerances) — no redeploys.
  3. Log-verify: in AdvantageScope, overlay goal vs position — you're done when the traces hug through the whole profile, not just at the ends.
⚠️ Tuning-sacred data

The shooter's interpolation maps (distance → hood angle / flywheel RPS / time-of-flight) are competition-proven measurements. Tuning sessions append or adjust points; they never restructure that code.

36Deploy & bring-up

  1. Connect to the robot (radio Wi-Fi or USB/Ethernet tether).
  2. Green build first: ./gradlew build. Never deploy red.
  3. Deploy: ./gradlew deploy — pushes the jar + the deploy/ folder (paths!) to the RIO.
  4. Before enabling, read the dashboard: zero config-verify alerts, zero disconnect alerts, correct alliance, an auto selected.
  5. First power-on of a new mechanism: mechanism at a known pose (boot seeds assume it — §21), hand on Enter (disable), first setpoints tiny, watch stator current live in AdvantageScope. Current limits + soft limits + config verify are the net — don't test the net.
  6. Verify direction conventions once per mechanism: positive = the geometric positive you declared (§13.4). If reversed, flip .inverted(...) — don't negate setpoints.

38Checklists

Adding a mechanism

  • Archetype chosen by physics (position / meters / speed / open-loop).
  • Constants file: data only — ids, ratios, gains (real+sim), budget, limits, tolerance.
  • Feedback: fused CANcoder, or ratio + boot seed.
  • Motion profile chosen (Expo default; trapezoid only for a fixed-speed spec; none for flywheels/rollers).
  • Current budget entered — with FOC torque peaks if that's the mode.
  • Soft limits + tolerance set; continuousWrap if it's a turret.
  • Sim model attached; verified moving in sim.
  • periodic() chained in the subsystem.

Before every commit

  • ./gradlew build green (compiles + tests).
  • Sim launches and behaves.
  • On a feature branch; one concern; explicit staging; message says why.

Before a match

  • Every device answers in Tuner X, licensed.
  • Zero config-verify / disconnect alerts.
  • Swerve constants robot-verified (offsets, inversions, coupling).
  • Every named command in the selected auto is registered.
  • Telemetry.init(true, …); TunableNumber tuning OFF.
  • Correct alliance on the DS; heading re-zeroed if needed.
