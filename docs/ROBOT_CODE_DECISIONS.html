🗡️ Decision-driven · conceptual · visual

Every choice, mapped to the field that expresses it.

You know how to program. This is the map from a physical question about your mechanism to the exact MechanismConfig call — plus the concepts and diagrams behind each one. Dark by default; toggle bottom-right.

1The architecture

Four layers, strict downward dependency. You live in the top two; the bottom two are the library's job and you never touch them.

2The model in 60 seconds

  • The loop lives on the motor. You pick a setpoint each iteration; the TalonFX runs the closed loop at 1 kHz. The RIO never runs a PID.
  • Everything is mechanism units. The device is told its ratio, so you command Radians/Meters/RotationsPerSecond, never ticks. Conversions do not exist in your code.
  • A mechanism is a value object + an IO. MechanismConfig is pure data; the archetype turns it into control requests. Real vs sim is chosen at construction — no replay, no AdvantageKit.
  • Config is a contract. Applied → read back → compared → retried, with a dashboard Alert on failure. A half-configured device is never silent.
  • State is a table, not ifs. Legal transitions are declared; everything else is denied and logged. Interlocks are guards on edges.
The single asterisk

Migrated mechanisms run ControlMode.VOLTAGE with gains ported from the old software PID. FOC is a one-field change after a SysId pass, because gain units change (V/unit → A/unit). Treat VOLTAGE as "works today," FOC as "tuned upgrade."

6Field: feedback source

?Is there an absolute encoder (CANcoder) on the mechanism?
YES
Fuse it: .fusedCANcoder(new CANDeviceId(encId), rotorToSensor, sensorToMech, Rotations.of(offset))
FusedCANcoder blends absolute + rotor → drift-free, survives power-cycle, no boot homing. Use for hood, turret, arms.
NO
Give the ratio: .rotorToMechanismRatio(r)
Relative position from the rotor only. Seed it at boot with resetPosition(...) or a limit-switch home. Fine for rollers, flywheels, drums.
Ratio meaning differs

rotorToSensor = rotor turns per CANcoder turn. sensorToMech = CANcoder turns per mechanism turn (1.0 if the CANcoder is on the output). rotorToMechanismRatio = rotor turns per mechanism unit (for linear: per metre).

8Field: motion (the profile)

?How should it approach the setpoint?
DEFAULT
new MotionConstraints(expoKV, expoKA) — MotionMagicExpo
Shaped by the motor's own kV/kA. Time-optimal, smooth at both ends, no tuned cruise. Pick this for positional moves unless you have a reason not to.
FIXED CRUISE
new MotionConstraints(cruise, accel, jerk) — trapezoidal
When you need a known, constant cruise speed — e.g. two mechanisms moving in lock-step, or a hard velocity cap for safety.
NONE
omit .motion(...)
Setpoint applied directly (position or velocity). Right for flywheels; wrong for anything with inertia you'd slam.

9Field: gains — what actually sums to the output

The motor output is the sum of a feedback term and up to four feedforward terms. Knowing which term fixes which symptom is the whole game.

SymptomTerm to touch
Doesn't quite reach / steady-state errorraise kP (then kI sparingly)
Oscillates / overshootsadd kD, lower kP
Won't start moving until a big error buildsadd kS
Lags behind a moving setpointkV (and kA for fast accel)
Arm/elevator sags or drifts when heldkG + correct GravityType
Get them from SysId, not guessing

mechanism.sysIdQuasistatic/Dynamic(subsystem, dir) logs to hoot; analyze for kS/kV/kA (+kG). Fill both the real and sim gain sets — sim never matches real friction.

10Field: gravity type

?How does gravity load this mechanism?
ARM
.withGravity(kG, GravityTypeValue.Arm_Cosine)
Load varies with angle (max horizontal, zero vertical). The device scales kG by cos θ — so your mechanism zero must be horizontal.
ELEVATOR
.withGravity(kG, GravityTypeValue.Elevator_Static)
Constant vertical load. Applied flat regardless of position.
DYNAMIC
new LinearExtension(config, () -> armAngle, kG) · gains kG = 0
A slide on a pivoting arm: gravity along the axis is kG·sin(armAngle). Applied as supplemental feedforward from your angle supplier.

12Fields: soft limits, wrap, tolerance

?Does the mechanism have travel limits?
ROTARY
.softLimits(Radians.of(min), Radians.of(max))
Enforced on the device. Goals are clamped before they're commanded.
LINEAR
.softLimitsMeters(Meters.of(min), Meters.of(max))
CONTINUOUS
.softLimits(...) + .continuousWrap()
Turret: commands wrap to the nearest equivalent inside the range — shortest legal path, never unwinds. Wrap needs limits set.
Tolerance = the "reached" window

.tolerance(Radians.of(0.02)) / .toleranceMeters(...) defines when atGoal/atSpeed flips true. Too tight → never "ready"; too loose → shoots early. Tune against the real mechanism's noise floor.

13Field: sim model

?What's the physical plant?
SPINNER
.simRotationalModel(gearbox, moi, gearing)
Flywheel, roller, drum, turret — pure rotational inertia.
ARM
.simArmModel(gearbox, gearing, moi, length, min, max, start)
Gravity-loaded pivot.
LIFT
.simElevatorModel(gearbox, gearing, mass, drumR, min, max, start)
Linear stage against gravity.
Estimates are fine

Sim exists to exercise logic (state machines, autos, readiness gating), not to be a physics thesis. Rough MOI/mass is enough. Sim always uses your sim gain set in VOLTAGE mode.

14State machine — the concept & the graph

A subsystem's modes are a directed graph with a default-deny edge set. Declaring the graph is the safety model.

ConceptMechanism
Default-denyOnly transition(a,b) edges are legal; a request for any other edge fails + logs. Illegal sequences can't happen.
GuardA BooleanSupplier on an edge. False → request goes pending and retries each periodic() until true. This is your interlock.
whileInA Command scheduled on entry, cancelled on exit — requirements respected.
Non-blockingEverything is edge-triggered + pending-retry. Nothing spins or sleeps.

16The loop — why order matters

The one rule that buys free latency

Refresh before the scheduler. Do it after (the naive way) and every command reads last loop's sensors. This single ordering is why the migrated code is measurably tighter than v1.

17Decisions → the finished config

Read the config as answers: rotary + absolute encoder + gravity arm + smooth + FOC-later + limited. Every line is a decision from above.

a hood, annotated by decision
new MechanismConfig("Hood", new CANDeviceId(30))       // §4  rotary → PositionalMechanism
    .controlMode(ControlMode.VOLTAGE)                   // §7  today; FOC after SysId
    .fusedCANcoder(new CANDeviceId(34), 12.8, 1.0, Rotations.of(-0.13))  // §6  absolute encoder present
    .gains(REAL_GAINS, SIM_GAINS)                       // §9  from SysId (real + sim)
    .motion(new MotionConstraints(3.0, 5.0))            // §8  Expo — smooth default
    .softLimits(Radians.of(0.0), Radians.of(0.9))       // §12 has travel limits, no wrap
    .tolerance(Radians.of(0.02))                        // §12 ready window
    .currentBudget(new CurrentBudget(40, 30))           // §11 small arm
    .simArmModel(DCMotor.getKrakenX60Foc(1), 74.9, 0.05, 0.15, 0.0, 0.9, 0.0); // §13 gravity arm
