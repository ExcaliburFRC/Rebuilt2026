How to build robot code, from nothing to a full robot.

A complete, no-steps-skipped guide to writing a competition robot on ExcaLib v2 — the team's Phoenix-6, FOC-first library where a subsystem is something you declare, not something you hand-wire.

📖 Read time ~45 min · skim in 10 🎯 Audience a brand-new programmer 🧰 Stack WPILib 2026 · Phoenix 6 · DogLog · maple-sim · PathPlanner
💡 How to read this

Go top to bottom the first time. Every part builds on the last. When you just need to add one subsystem, jump to Part 4 then use the option tables in Appendix A. Every code block has a Copy button. Toggle dark mode and jump to the top with the buttons in the bottom-right.

0Before you start

You cannot write robot code on a blank machine. Install these once, in order. Skip nothing.

0.1 · Install the software

  1. WPILib 2026 Download the full VS Code + tools bundle from github.com/wpilibsuite/allwpilib/releases. This gives you the 2026 JDK (at C:\Users\Public\wpilib\2026\jdk), the build system, and the simulator. Use this JDK — see the warning below.
  2. CTRE Phoenix Tuner X From the Microsoft Store. You need it to license devices, set CAN IDs, run diagnostics, and generate swerve constants.
  3. A JetBrains IDE or VS Code IntelliJ IDEA or VS Code both work. This project is a standard Gradle project.
  4. Git You will branch, commit, and push. Install Git and sign in to GitHub.
  5. AdvantageScope The log/telemetry viewer. Install from github.com/Mechanical-Advantage/AdvantageScope. You will live in this.
  6. Elastic dashboard (optional) A driver dashboard that reads NetworkTables and renders WPILib Alerts natively.
🚫 The one gotcha that wastes an afternoon (Windows)

Gradle must run tests and simulation on the WPILib JDK. Any other JDK ships an incompatible MSVC runtime that hard-crashes wpiHal.dll on load with Invalid MSVC Runtime. The test task is already pinned in build.gradle; for the sim, always pass the JDK explicitly (shown in Part 1).

⚠️ Two buses, two ID spaces

An ID is only unique within a bus. The swerve CANivore and the RIO bus both have a device "10" and that is fine — they never collide because CANDeviceId always carries the bus name. Never mix them up.

2The mental model

Understand this and the rest of the handbook is just syntax.

2.1 · The library is a stack of layers

Each layer only talks to the one below it. You spend almost all your time in the top two.

Superstructure robot-wide goals
One brain. "The robot's goal is SHOOT_HUB." It fans that out to every subsystem.
Subsystems + State machines one mechanism's behavior
"The intake is OPEN." Each subsystem owns its mechanisms and a state machine.
Mechanism archetypes how a thing moves
Positional, Linear, Velocity, Roller. You configure one; it does the control.
Device layer talking to the motor
Motor (TalonFX wrapper), verified config, batched status signals. You never touch this.

2.2 · "Declare, don't write"

In the old library you wrote the control loop by hand in every subsystem. In v2 you declare a config object and the archetype runs the loop for you — on the motor controller, at 1 kHz, with FOC. Adding a mechanism is filling in a form, not writing plumbing.

🧾You provide

Device IDs, gear ratios, gains, motion limits, current budget, soft limits, a sim model.

⚙️The library provides

Config apply + verify + retry, signal management, telemetry, disconnect alerts, SysId, simulation.

🎯Result

A subsystem that reads as configuration + state declarations. No PID math in your code.

2.3 · The control philosophy (why it's fast & smooth)

  • The loop runs on the motor, not the RIO. You pick a setpoint; the TalonFX closes the loop at 1 kHz. No 50 Hz RIO PID.
  • Everything is in mechanism units. The device is told its gear ratio (SensorToMechanismRatio), so you command radians or meters, never encoder ticks.
  • MotionMagic profiles every move. Positional moves default to MotionMagicExpo — time-optimal and smoother than a trapezoid.
  • FOC by default, Voltage always available. Real hardware uses TorqueCurrentFOC; simulation forces Voltage. Same code path.
  • Config is verified. Every device config is applied, read back, compared, and retried — with a dashboard alert if it fails.
🧠 The one asterisk right now

Every migrated mechanism currently runs in VOLTAGE mode with gains ported from the old software PID. Switching to FOC is a one-line config change after a SysId session, because gains do not transfer between modes. See Part 10.

3The building blocks

Five small value objects describe any mechanism. Learn these and you can configure anything.

💡 No factory methods — ever

Team style: construct with new, configure with instance methods. There is no Gains.of(...) or a builder. If you reach for a static factory, stop.

3.1 · CANDeviceId — id + bus, together

examples
new CANDeviceId(30);                     // device 30 on the RIO CAN bus ("")
new CANDeviceId(11, "SwerveCANivore");   // device 11 on the CANivore

Keeping the bus attached to the id makes "right id, wrong bus" impossible.

3.2 · Gains — the control gains

Gains examples
new Gains();                          // all zero
new Gains(kP, kI, kD);                 // feedback only
new Gains(kP, kI, kD, kS, kV, kA);     // + static / velocity / accel feedforward
new Gains(10.8, 0, 0.15).withGravity(0.3125, GravityTypeValue.Arm_Cosine);
GainDoes
kP kI kDFeedback: how hard to correct position/velocity error.
kSStatic friction — the push needed just to start moving.
kVVelocity feedforward — output per unit of target speed.
kAAcceleration feedforward.
kG + GravityTypeGravity: Arm_Cosine (scaled by cos of angle, zero = horizontal) for arms/pivots, Elevator_Static (constant) for elevators.
🚫 Gains do not cross control modes

A VOLTAGE gain is volts-per-unit; a FOC gain is amps-per-unit. They are different numbers. Every config carries two gain sets — real and sim — and you re-derive them per mode with SysId.

3.3 · MotionConstraints — the motion profile

MotionConstraints
new MotionConstraints(cruiseVel, accel, jerk);   // TRAPEZOIDAL (3 args)
new MotionConstraints(expoKV, expoKA);            // EXPONENTIAL / MotionMagicExpo (2 args)
new MotionConstraints(expoKV, expoKA).withCruiseCap(maxVel);  // Expo, speed-capped
🧠 Which one?

Expo (2-arg) is the default for positional moves — it's shaped by the motor's own kV/kA, so it's time-optimal and gentle at both ends. Use trapezoidal (3-arg) only when you want a fixed cruise speed, e.g. two mechanisms moving in lock-step. Units are mechanism units (rot/s, rot/s²) — for a linear mechanism that's m/s, m/s².

3.4 · CurrentBudget — current & breaker protection

CurrentBudget
new CurrentBudget(statorLimit, supplyLimit);                 // amps
new CurrentBudget(80, 60).withSupplyLower(40, 1.0);          // drop to 40A after 1s over-limit
new CurrentBudget(120, 80).withTorquePeaks(120, -120);      // FOC output clamp
LimitProtects
StatorTorque & heat. Your main "how strong may this be" knob.
Supply + lower/timeThe breaker & battery. Drops the draw after sustained over-limit — brownout protection.
Torque peaksHard output clamp for TorqueCurrentFOC (which bypasses the stator limit by design).
💡 Keep every mechanism's amps in one place

Put the numbers in the subsystem's Constants file so the whole robot's current budget is reviewable at a glance. (Idea borrowed from Team 6328.)

3.5 · ControlMode — which request family

ModeUse
TORQUE_CURRENT_FOCThe library default on real hardware (Phoenix Pro). Torque-native, immune to voltage sag.
VOLTAGESimulation (forced) and debugging; the fallback path. Where all migrated mechanisms sit today.
DUTY_CYCLEBring-up only.

4Your first subsystem — a hood, end to end

A hood is a pivoting arm: perfect for the PositionalMechanism archetype. Follow every step; this is the template for everything.

  1. Create the constants file Data only — no hardware objects, no logic. One file per subsystem.
    subsystems/hood/HoodConstants.java
    package frc.robot.subsystems.hood;

import com.ctre.phoenix6.signals.GravityTypeValue;
import frc.excalib2.control.*;

public class HoodConstants {
    public static final int MOTOR_ID   = 30;
    public static final int ENCODER_ID = 34;

    // rotor rotations per hood rotation (from the gearbox + belt)
    public static final double ROTOR_TO_MECHANISM = 74.9;

    // VOLTAGE-mode gains (ported); re-derive for FOC with SysId later
    public static final Gains REAL_GAINS = new Gains(68, 0, 0.9)
            .withGravity(0.31, GravityTypeValue.Arm_Cosine);
    public static final Gains SIM_GAINS  = new Gains(40, 0, 0);

    public static final MotionConstraints MOTION = new MotionConstraints(3.0, 5.0); // Expo kV, kA
    public static final CurrentBudget BUDGET = new CurrentBudget(40, 30);
}
  2. Declare the mechanism The whole control setup is this one config object.
    subsystems/hood/Hood.java
    package frc.robot.subsystems.hood;

import edu.wpi.first.math.system.plant.DCMotor;
import edu.wpi.first.units.measure.Angle;
import edu.wpi.first.wpilibj2.command.Command;
import edu.wpi.first.wpilibj2.command.SubsystemBase;
import edu.wpi.first.wpilibj2.command.button.Trigger;
import frc.excalib2.control.ControlMode;
import frc.excalib2.device.CANDeviceId;
import frc.excalib2.mechanisms.MechanismConfig;
import frc.excalib2.mechanisms.PositionalMechanism;

import java.util.function.Supplier;
import static edu.wpi.first.units.Units.Radians;
import static frc.robot.subsystems.hood.HoodConstants.*;

public class Hood extends SubsystemBase {
    private final PositionalMechanism hood = new PositionalMechanism(
        new MechanismConfig("Hood", new CANDeviceId(MOTOR_ID))
            .controlMode(ControlMode.VOLTAGE)                 // FOC after SysId
            .rotorToMechanismRatio(ROTOR_TO_MECHANISM)
            .gains(REAL_GAINS, SIM_GAINS)
            .motion(MOTION)
            .softLimits(Radians.of(0.0), Radians.of(0.9))
            .currentBudget(BUDGET)
            .tolerance(Radians.of(0.02))
            .simArmModel(DCMotor.getKrakenX60Foc(1), ROTOR_TO_MECHANISM, 0.05, 0.15, 0.0, 0.9, 0.0));

    public Command aimAt(Supplier<Angle> target) {
        return run(() -> hood.setGoal(target.get()));
    }
    public Trigger atGoal() { return hood.atGoal; }

    @Override public void periodic() {
        hood.periodic();   // telemetry + disconnect alerts + sim step — required
    }
}
  3. That's the whole subsystem. No PID objects, no encoder reads, no conversion factors, no config-apply code. The archetype did all of it.
  4. Bind it (temporarily) to test In RobotContainer, drive it from a button while you tune.
    RobotContainer.java (snippet)
    private final Hood hood = new Hood();
// ...
controller.triangle().whileTrue(hood.aimAt(() -> Radians.of(0.5)));
  5. Run it in simulation ./gradlew simulateJava …, open AdvantageScope, and watch Hood/PositionRotations track Hood/GoalRotations. It moves because you gave it a simArmModel.
✅ You just built a subsystem

Config + one command + one periodic() call. Everything else in this handbook is variations on these five steps.

5Every archetype (with all the options)

Pick the archetype that matches the physics of your mechanism. Here is each one, in full.

🦾PositionalMechanism

Arm · pivot · hood · turret. Moves to an angle.

🛗LinearExtension

Elevator · slide · telescope. Moves to a length in meters.

🌀VelocityMechanism

Flywheel · drum. Holds a speed.

🎢RollerMechanism

Intake · feeder. Open-loop output + game-piece detection.

5.1 · PositionalMechanism (arm / pivot / hood / turret)

Configured in Part 4. Two extras worth knowing:

Fused CANcoder (absolute position)

If the mechanism has an absolute encoder, fuse it so position survives a power cycle and never drifts:

config snippet
.fusedCANcoder(new CANDeviceId(ENCODER_ID), rotorToSensorRatio, sensorToMechanismRatio,
               Rotations.of(magnetOffset))

Continuous wrap (turret)

A turret should take the shortest legal path to a target and not unwind. Add one line and goals wrap to the nearest equivalent inside the soft-limit range:

config snippet
.softLimits(Radians.of(-5.4), Radians.of(1.5))
.continuousWrap()

API: setGoal(Angle), setGoalRotations(double), atGoal (Trigger), getPosition(), getVelocityRotationsPerSecond(), resetPosition(Angle), stop().

5.2 · LinearExtension (elevator / slide)

Same idea as positional but the unit is meters. Configure the device with rotor-rotations-per-meter and use the *Meters helpers.

Elevator.java (excerpt)
private final LinearExtension lift = new LinearExtension(
    new MechanismConfig("Elevator", new CANDeviceId(50))
        .controlMode(ControlMode.VOLTAGE)
        .rotorToMechanismRatio(ROTOR_PER_METER)
        .gains(new Gains(30, 0, 0, 0, 12, 0).withGravity(0.4, GravityTypeValue.Elevator_Static), SIM_GAINS)
        .motion(new MotionConstraints(2.0, 4.0))         // m/s, m/s²
        .softLimitsMeters(Meters.of(0), Meters.of(1.2))
        .toleranceMeters(Meters.of(0.01))
        .simElevatorModel(DCMotor.getKrakenX60Foc(2), ROTOR_PER_METER, 5.0, 0.02, 0, 1.2, 0));

public Command goTo(Distance height) { return run(() -> lift.setLength(height)); }
🧠 Two gravity modes

Constant gravity (vertical elevator): put kG with Elevator_Static in the gains — the controller holds it onboard. Dynamic gravity (a slide mounted on a pivoting arm): use the second constructor new LinearExtension(config, armAngleSupplier, kG) — it applies kG·sin(angle) as supplemental feedforward, and you keep the gains' kG at 0.

API: setLength(Distance), setLengthMeters(double), atGoal, getLength(), getVelocityMetersPerSecond(), resetLength(Distance).

5.3 · VelocityMechanism (flywheel / drum)

Flywheel.java (excerpt)
private final VelocityMechanism flywheel = new VelocityMechanism(
    new MechanismConfig("Flywheel", new CANDeviceId(31))
        .follower(new CANDeviceId(32), false)            // a second motor, same shaft
        .controlMode(ControlMode.VOLTAGE)
        .rotorToMechanismRatio(1.2)
        .gains(new Gains(0.2, 0, 0, 0.33, 0.156, 0), SIM_GAINS)
        .currentBudget(new CurrentBudget(120, 80))
        .tolerance(Rotations.of(2))                      // "at speed" window, rot/s
        .simRotationalModel(DCMotor.getKrakenX60Foc(2), 0.01, 1.2));

public Command spinUp(double rps) { return run(() -> flywheel.setVelocityRotationsPerSecond(rps)); }
public Trigger atSpeed() { return flywheel.atSpeed; }
💡 Profiled or instant?

If you give .motion(...), spin-up is jerk-limited (MotionMagicVelocity). With no motion constraints, the setpoint is applied directly. Flywheels usually want it direct; a heavy drum wants a ramp.

API: setVelocity(AngularVelocity), setVelocityRotationsPerSecond(double), atSpeed, getVelocity(), stop().

5.4 · RollerMechanism (intake / feeder)

Roller.java (excerpt)
private final RollerMechanism roller = new RollerMechanism(
    new MechanismConfig("Intake/Roller", new CANDeviceId(13))
        .controlMode(ControlMode.VOLTAGE)
        .currentBudget(new CurrentBudget(80, 30))
        .simRotationalModel(DCMotor.getKrakenX60Foc(1), 0.002, 3.0));

public Command intake()  { return runEnd(() -> roller.runDutyCycle(0.8), roller::stop); }
// A game piece stalls the roller → current spikes. Detect it:
public Trigger hasPiece() { return roller.currentSpike(40, 0.2); }  // 40A held for 0.2s

API: runVolts(double), runAmps(double), runDutyCycle(double), stop(), getStatorAmps(), currentSpike(amps, seconds) → Trigger.

⚠️ Two things every archetype needs

(1) Call the mechanism's periodic() from your subsystem's periodic(). (2) Give it a simModel so it works in simulation. Forget either and things silently don't move.

6State machines

A subsystem usually has a handful of named modes. Declare them once; the machine enforces the rules.

6.1 · Declare it

Intake.java (excerpt)
public enum IntakeState { CLOSED, OPEN, PUMP }

private final StateMachine<IntakeState> machine =
    new StateMachine<>("Intake", IntakeState.CLOSED)
        .onEnter(IntakeState.OPEN,   () -> fourBar.setGoal(OPEN_ANGLE))
        .whileIn(IntakeState.PUMP,   pumpCommand())          // a Command, scheduled on entry
        .onExit(IntakeState.PUMP,    roller::stop)
        .transition(IntakeState.CLOSED, IntakeState.OPEN)     // legal edge
        .transition(IntakeState.OPEN,   IntakeState.PUMP, armHomed)  // guarded edge
        .transitionFromAny(IntakeState.CLOSED);               // always-legal escape

@Override public void periodic() {
    fourBar.periodic();
    machine.periodic();   // ticks the machine — required
}

6.2 · The rules

ConceptMeaning
Default-denyA transition you didn't declare is illegal. Requesting it fails and is logged. Illegal sequences are impossible by construction.
Guard (a BooleanSupplier)An edge can be gated. If the guard is false, the request goes pending and retries every loop until it passes.
onEnter / onExitA Runnable that fires once at the transition.
whileInA Command scheduled on entry and cancelled on exit. Requirements work as usual.
transitionFromAnyAn edge into a state from everywhere — e.g. an emergency IDLE.

6.3 · Drive it from commands / triggers

usage
machine.requestCommand(IntakeState.OPEN);        // instant request (Command)
machine.requestAndWaitCommand(IntakeState.OPEN); // finishes when the state is reached
machine.in(IntakeState.PUMP);                    // a Trigger, true while in PUMP
machine.getCurrentState();                        // current enum value
machine.forceState(IntakeState.CLOSED);          // bypass the table (reset / recovery only)
🧠 Startup

The initial state's onEnter/whileIn fire on the machine's first periodic() or first request() — declare everything first, then let it tick.

7The superstructure — one brain for the robot

The superstructure turns a single robot goal into coordinated states across every subsystem, and makes illegal combinations impossible.

7.1 · A goal is a tuple of subsystem states

superstructure/RobotState.java
public enum RobotState {
    IDLE      (IntakeState.CLOSED, ShooterState.IDLE,      TransportState.IDLE),
    AIM_HUB   (IntakeState.CLOSED, ShooterState.LOOK_HUB,  TransportState.IDLE),
    SHOOT_HUB (IntakeState.PUMP,   ShooterState.SHOOT_HUB, TransportState.FEED);

    final IntakeState intake; final ShooterState shooter; final TransportState transport;
    RobotState(IntakeState i, ShooterState s, TransportState t){ intake=i; shooter=s; transport=t; }
}
🧠 Illegal states can't exist

Because a goal is a fixed tuple, a nonsensical combination (say, "intake open while climbing") simply has no enum entry. It's uncommandable — you can't even type it.

7.2 · Fan the goal out

superstructure/Superstructure.java (core)
public class Superstructure extends frc.excalib2.superstructure.Superstructure<RobotState> {
    // build a StateMachine<RobotState> whose onEnter pushes each field to a subsystem:
    for (RobotState goal : RobotState.values()) {
        machine.onEnter(goal, () -> {
            shooter.requestState(goal.shooter);
            transport.requestState(goal.transport);
            intake.requestState(goal.intake);
        });
        machine.transitionFromAny(goal);
    }
}
// request a goal from anywhere:
superstructure.request(RobotState.SHOOT_HUB);

7.3 · Interlocks are guards

Want "only feed once the shooter is ready"? That's a guard on the transport's FEED edge — not an if scattered through your code:

guard example
.transition(TransportState.IDLE, TransportState.FEED, shooter.ready())

7.4 · Wire the buttons & zones

trigger wiring
intakeButton.and(inAllianceZone).and(hubActive)
            .onTrue(superstructure.request(RobotState.SHOOT_HUB));
💡 Auto and teleop use the same path

Autonomous named commands call superstructure.request(goal) too — so auto and teleop behavior can never drift apart.

8The drivetrain

Swerve is built on the CTRE SwerveDrivetrain (250 Hz odometry, built-in sim) and wrapped as SwerveSubsystem with every drive command you need.

8.1 · Generate the constants

  1. Run Tuner X → Swerve project generator on the real robot to measure offsets, inversions, and the drive/steer ratios. It produces a TunerConstants-style file.
  2. Put the numbers in SwerveConfig.java — the drivetrain constants plus four module constants (steer id, drive id, CANcoder id, location).
🚫 Verify on the robot before driving

The current SwerveConfig is hand-derived from the old library and is not yet robot-verified: module inversions, CANcoder offsets, and the coupling ratio all need a bench check. Do that before a real drive.

8.2 · Construct it and drive

RobotContainer.java (swerve)
public final SwerveSubsystem swerve = new SwerveSubsystem(
    SwerveConfig.DRIVETRAIN,
    SwerveConfig.FRONT_LEFT, SwerveConfig.FRONT_RIGHT,
    SwerveConfig.BACK_LEFT,  SwerveConfig.BACK_RIGHT);

// default teleop drive (deadband is rescaled — no jump at the edge):
swerve.setDefaultCommand(swerve.fieldCentricDriveCommand(
    () -> -controller.getLeftY(), () -> -controller.getLeftX(), () -> -controller.getRightX(),
    MAX_SPEED_MPS, MAX_OMEGA_RAD_PER_SEC, DEADBAND));

8.3 · All the drive commands

CommandDoes
fieldCentricDriveCommand(...)Field-relative teleop, operator-perspective aware (auto-flips for red).
robotCentricDriveCommand(...)Robot-relative teleop.
headingLockedDriveCommand(...)Translate freely while the heading locks onto a target direction.
driveToPoseCommand(...)Short-range precision move-to-pose (profiled PID).
pathfindToPoseCommand(...)PathPlanner pathfinding around obstacles to a pose.
pathfindThenFollowPathCommand(...)Pathfind to a path's start, then follow it. Missing file → alert, not a crash.
pathfindWithOverrideCommand(...)Pathfind, but the driver can take over with the sticks and it resumes on release.
brakeCommand() / idleCommand()X-stance to resist pushing / coast.
resetHeadingCommand() / resetPoseCommand(...)Re-zero field-forward / overwrite odometry (work while disabled).
coastCommand()Coast all modules while held — push the robot around the pit.

Getters: getPose(), getHeading(), getSpeeds(), getVelocityMagnitude().

8.4 · Vision — Limelight MegaTag2

Enable pose fusion in the RobotContainer constructor. For a turret-mounted camera you also supply the turret-corrected heading and a pose transform:

vision wiring
swerve.withLimelight(
        "limelight-turret",
        () -> swerve.getHeading().plus(TurretOffsetGetter.instance.getTurretOffset()),
        TurretOffsetGetter.instance::isFast)          // reject estimates while spinning fast
     .withVisionPoseTransform(SwerveConfig::turretPoseToRobotPose);

MegaTag2 std-devs scale with distance and tag count automatically. swerve.sawTagRecently(2.5) gives a Trigger for "we had a vision fix in the last 2.5s".

9Autonomous

PathPlanner drives the wheels; named commands run your superstructure at the right moments.

  1. Draw paths & autos in the PathPlanner app — they save into src/main/deploy/pathplanner/.
  2. Register named commands BEFORE building the chooser.
    RobotContainer.registerCommands()
    NamedCommands.registerCommand("shoot",  superstructure.request(RobotState.SHOOT_HUB));
NamedCommands.registerCommand("intake", superstructure.request(RobotState.INTAKE_AIM_HUB));
NamedCommands.registerCommand("idle",   superstructure.request(RobotState.IDLE));
  3. Build the chooser. The Autos helper populates it from every .auto file with a safe "Do Nothing" default.
🚫 The bug that already bit us once

If a named command referenced in a .auto isn't registered, PathPlanner silently substitutes a no-op — your auto drives but never intakes or shoots, with no error. Always register before building, and confirm every name in your autos has a registration.

10Telemetry & tuning

10.1 · Logging — DogLog is the log of record

Start it once in the robot constructor; then log anything with one call. Mechanisms log their own basics automatically.

logging
Telemetry.init(false, powerDistributionHub);   // (isCompetition, PDH for power logging)
DogLog.log("Shooter/DistanceToTarget", distance);
DogLog.log("Superstructure/Goal", currentGoal().name());

Phoenix SignalLogger (started by Telemetry.init) captures high-rate device data to .hoot files. Open both in AdvantageScope.

💡 At competition

Pass true to Telemetry.init — it stops NetworkTables publishing (bandwidth) and logs to file only.

10.2 · Live tuning without redeploying

TunableNumber
TunableNumber.enableTuning();                         // dev builds only, once at startup
private final TunableNumber kFlywheelRps = new TunableNumber("Shooter/FlywheelRPS", 38);
// ... read it live from AdvantageScope / Elastic:
flywheel.setVelocityRotationsPerSecond(kFlywheelRps.get());

10.3 · Fault & health monitoring

Every Motor auto-registers with FaultReporter. Disconnects, over-temp, brownout, and CAN-bus utilization all surface as dashboard Alerts. You just call FaultReporter.poll() in the loop (already wired).

10.4 · Tuning a mechanism (SysId → gains → FOC)

  1. Run SysId — every mechanism exposes sysIdQuasistatic(subsystem, dir) and sysIdDynamic(subsystem, dir); the swerve has sysIdTranslation/sysIdSteer. Data lands in the hoot log.
  2. Analyze in AdvantageScope / Tuner X to get kS, kV, kA (and kG for arms/elevators).
  3. Fill in the gains in the subsystem's constants — real set and sim set.
  4. Flip to FOC — change .controlMode(ControlMode.VOLTAGE) to TORQUE_CURRENT_FOC and re-run SysId, because the gain units change from volts to amps.
🧠 Why VOLTAGE first

The migrated mechanisms carry the old software-PID gains, which are voltage-based. They work today. FOC is strictly better but needs its own characterization — so we ship on VOLTAGE and upgrade per mechanism.

11Simulation

Every mechanism can run in a physics sim, so you test control logic and autos without a robot.

11.1 · Give each mechanism a model

HelperFor
.simRotationalModel(gearbox, moi, gearing)Flywheel, roller, drum, turret.
.simArmModel(gearbox, gearing, moi, length, min, max, start)Arm / pivot / hood (gravity-loaded).
.simElevatorModel(gearbox, gearing, mass, drumR, min, max, start)Elevator / linear extension.

11.2 · The drivetrain & the field

The CTRE swerve simulates itself (5 ms thread). maple-sim adds a full physics arena — robot collisions and game pieces — for testing intake interaction and auto-alignment. Run everything with simulateJava and watch it in AdvantageScope's 3D field.

💡 Sim uses different gains

Simulation forces VOLTAGE mode and uses the sim gain set from your config — sim physics never matches real friction/inertia, so keeping them separate is intentional.

12Wiring it all together

12.1 · The robot loop — order matters

Robot.robotPeriodic() runs this exact sequence. The signal refresh before the scheduler is what removes ~20 ms of sensor latency.

SignalHub.refreshAll()→ FaultReporter.poll()→ ShiftUtil.update()→ CommandScheduler.run()→ LoopTimer.end()
🧠 Why refresh first

If you refresh signals after the scheduler (the old way), every command acts on last loop's sensor data. Refreshing first means commands see fresh values — free latency reduction.

12.2 · One-time boot setup

Robot() constructor
Telemetry.init(false, null);
AllianceFlip.configure(FIELD_LENGTH_METERS, FIELD_WIDTH_METERS);   // season field dims
robotContainer = new RobotContainer();
SignalHub.optimizeAll();     // disable unused CAN signals — do this AFTER all devices exist

12.3 · The RobotContainer checklist

  • Construct subsystems + the swerve + the superstructure.
  • Wire vision + configureAutoBuilder on the swerve.
  • registerCommands() then build the auto chooser.
  • Set the swerve default command and bind buttons/zones to superstructure requests.
  • Own a LedStrip and bind patterns to state triggers.

13Deploy to the robot

  1. Connect to the robot radio (Wi-Fi) or a USB/Ethernet tether.
  2. Confirm the build is green: ./gradlew build. Never deploy red code.
  3. Deploy: ./gradlew deploy. It builds a fat jar and pushes it to /home/lvuser on the roboRIO, plus the deploy/ folder (paths, settings).
  4. Enable in the Driver Station and watch the AdvantageScope live feed + the Alerts widget.
  5. Coast the mechanisms (bind coastCommand) so you can back-drive them by hand for zeroing.
🚫 First power-on of anything that moves

Current limits, soft limits, and the config-verify alert are your safety net — but the first time a new mechanism is enabled, keep a hand on the Driver Station Enter (disable) key and start with tiny setpoints.

15Checklists

15.1 · Before every commit

  • ./gradlew build is green (compiles + tests pass).
  • The sim still launches and drives.
  • You're on a feature branch, not main.
  • One concern per commit; the message says what & why.
  • You staged files explicitly — no stray scratch files swept in with git add -A.

15.2 · Adding a subsystem

  • Constants file holds data only (no hardware objects, no logic).
  • The mechanism has a simModel.
  • Current budget numbers are in the constants, not inline.
  • The subsystem's periodic() calls the mechanism's (and the machine's) periodic().
  • Gains have a real set and a sim set.
  • A RobotState tuple exists if it participates in robot goals.

15.3 · Before a match (robot verified)

  • Every device is licensed (Phoenix Pro) and answers in Tuner X.
  • Swerve constants verified on the robot: inversions, CANcoder offsets, coupling ratio.
  • Every named command in every selected auto is registered.
  • Soft limits & current limits set on all articulated mechanisms.
  • Telemetry.init(true, …) for competition (NT publishing off).
  • No config-verify or disconnect alerts on the dashboard.
