🫀 One real subsystem · every part explained

The Intake, dissected — what each line does and why it's there.

This is the actual migrated Intake.java from the robot — a four-bar, a roller, and a three-state machine. High-level and declarative on the surface; here's the depth and the reasoning under every line.

0The whole file, once

A complete competition subsystem — two motors on the four-bar, a roller, and a coordinating state machine — in ~80 lines. Read it once; we'll take it apart below.

frc/robot/subsystems/intake/Intake.java
public class Intake extends SubsystemBase {

    private final PositionalMechanism fourBar = new PositionalMechanism(
            new MechanismConfig("Intake/FourBar", new CANDeviceId(LEFT_FOUR_BAR_MOTOR_ID))
                    .follower(new CANDeviceId(RIGHT_FOUR_BAR_MOTOR_ID), true)
                    .controlMode(ControlMode.VOLTAGE)              // ported v1 volts gains; FOC after SysId
                    .rotorToMechanismRatio(GEARING)
                    .gains(FOUR_BAR_GAINS, FOUR_BAR_SIM_GAINS)
                    .motion(FOUR_BAR_MOTION)
                    .softLimits(Radians.of(INTAKE_MIN_ANGLE_RAD), Radians.of(INTAKE_MAX_ANGLE_RAD))
                    .peakVoltage(FOUR_BAR_PEAK_VOLTS, -FOUR_BAR_PEAK_VOLTS)
                    .currentBudget(FOUR_BAR_BUDGET)
                    .tolerance(Radians.of(INTAKE_ANGLE_TOLERANCE_RAD))
                    .neutralMode(Coast)
                    .simArmModel(DCMotor.getKrakenX60Foc(2), GEARING, 0.3, 0.3,
                            INTAKE_MIN_ANGLE_RAD, INTAKE_MAX_ANGLE_RAD, START_ANGLE_RAD));

    private final RollerMechanism roller = new RollerMechanism(
            new MechanismConfig("Intake/Roller", new CANDeviceId(ROLLER_MOTOR_ID))
                    .controlMode(ControlMode.VOLTAGE)
                    .currentBudget(ROLLER_BUDGET)
                    .simRotationalModel(DCMotor.getKrakenX60Foc(1), 0.002, 3.0));

    private final StateMachine<IntakeStates> machine;
    public final Trigger atPositionTrigger;

    public Intake() {
        fourBar.resetPosition(Radians.of(START_ANGLE_RAD));

        machine = new StateMachine<>("Intake", CLOSE)
                .whileIn(OPEN,  run(() -> { fourBar.setGoal(Radians.of(OPEN.angle));  roller.runDutyCycle(OPEN.voltage); }))
                .whileIn(CLOSE, run(() -> { fourBar.setGoal(Radians.of(CLOSE.angle)); roller.runDutyCycle(CLOSE.voltage); }))
                .whileIn(PUMP,  pumpCommand())
                .transitionFromAny(OPEN)
                .transitionFromAny(CLOSE)
                .transitionFromAny(PUMP);

        atPositionTrigger = new Trigger(() -> Math.abs(
                machine.getCurrentState().angle - fourBar.getPosition().in(Radians)) < INTAKE_ANGLE_TOLERANCE_RAD);
    }

    private Command pumpCommand() {
        return Commands.repeatingSequence(
                run(() -> { fourBar.setGoal(Radians.of(PUMP_HIGH_ANGLE_RAD)); roller.runDutyCycle(PUMP.voltage); }).withTimeout(PUMP_PERIOD_SECONDS),
                run(() -> { fourBar.setGoal(Radians.of(PUMP_LOW_ANGLE_RAD));  roller.runDutyCycle(PUMP.voltage); }).withTimeout(PUMP_PERIOD_SECONDS))
            .withName("Intake Pump");
    }

    public Command setStateCommand(IntakeStates state) { return machine.requestCommand(state); }
    public void requestState(IntakeStates state)       { machine.request(state); }
    public Command coastCommand()                      { return fourBar.coastCommand(this); }

    @Override public void periodic() {
        fourBar.periodic();
        roller.periodic();
        machine.periodic();
    }
}
🧠 The thing to notice

There is no control code here. No PID objects, no encoder reads, no unit conversions, no config-apply calls, no follower wiring, no simulation stepping. Every one of those exists — it just lives in the archetype. This file is declarations (what the hardware is, how it should behave) and coordination (the state machine). That's the whole point.

2The constants — where the numbers come from

Every number lives in IntakeConstants.java, which holds data only — no hardware, no logic. That separation is deliberate: the subsystem reads as behavior, the constants read as a spec sheet.

IntakeConstants.java (excerpt)
public static final double GEARING = 14.14;              // rotor rotations per four-bar rotation
public static final double START_ANGLE_RAD = Math.PI - 0.732601 - 0.159;   // v1 stow seed
public static final double INTAKE_ANGLE_TOLERANCE_RAD = 0.003;

// Ported v1 gains (volts): kP 2 V/rad → ×2π = V/rotation ; kG 0.8 arm-cosine
public static final Gains FOUR_BAR_GAINS = new Gains(2 * 2 * Math.PI, 0, 0)
        .withGravity(0.8, GravityTypeValue.Arm_Cosine);
public static final Gains FOUR_BAR_SIM_GAINS = new Gains(30, 0, 0)
        .withGravity(0.3, GravityTypeValue.Arm_Cosine);

// v1 clamped speed two ways: ±1.5 rad/s velocity AND a ±1.5 V output clamp — both ported
public static final MotionConstraints FOUR_BAR_MOTION = new MotionConstraints(Units.radiansToRotations(1.5), 2.0, 0);
public static final double FOUR_BAR_PEAK_VOLTS = 1.5;

public static final CurrentBudget FOUR_BAR_BUDGET = new CurrentBudget(80, 60);
🧠 Why kP = 2 * 2 * Math.PI instead of just 2?

The old library's PID ran in radians (kP = 2 V/rad). The device now works in rotations (mechanism units), so the same physical stiffness is 2 V/rad × 2π rad/rot = 4π V/rot. Writing the conversion inline as 2 * 2 * Math.PI keeps the provenance visible: "this is the v1 gain, converted." A bare 12.57 would hide where it came from.

💡 Two gain sets, always

FOUR_BAR_GAINS (real) and FOUR_BAR_SIM_GAINS (sim) are different numbers on purpose — sim physics never matches real friction/inertia. The archetype picks the sim set automatically when running in simulation.

3Four-bar · construction & the name

Intake.java
private final PositionalMechanism fourBar = new PositionalMechanism(
        new MechanismConfig("Intake/FourBar", new CANDeviceId(LEFT_FOUR_BAR_MOTOR_ID))

Two constructions in one: a MechanismConfig (pure data), fed to a PositionalMechanism (which turns it into live control).

ArgumentWhat · why
"Intake/FourBar"The telemetry path. Everything the archetype logs — position, goal, applied volts, current, temperature, at-goal, disconnect alert — appears under this key in DogLog / AdvantageScope. Also the name in the config-verify alert. A good name here is free observability.
new CANDeviceId(LEFT_FOUR_BAR_MOTOR_ID)The leader motor's id + bus, together. No bus given → the RIO bus (""). The id-and-bus-as-one-value type makes "right id, wrong bus" impossible.
💡 The field is final and built inline

The mechanism is constructed at field-initialization, before the constructor body. That's fine — it does device I/O (config apply) eagerly, which is exactly when you want it (fail fast, surface alerts at boot).

4Four-bar · the follower

.follower(...)
.follower(new CANDeviceId(RIGHT_FOUR_BAR_MOTOR_ID), true)

The four-bar is driven by two Krakens (ids 10 and 34) on the same shaft. This one line says "there's a second motor; make it mirror the first."

🧠 Why opposed = true?

The two motors sit on opposite sides of the mechanism, so their gearboxes spin in mechanically opposite directions to produce the same four-bar motion. opposed=true tells the follower to invert relative to the leader. Get this wrong and the two motors fight each other — you'll see huge current and no motion. It's a physical fact about the gearbox mounting, encoded in one boolean.

💡 What the library does with this

It constructs a second Motor with the same verified configuration, then issues a Phoenix Follower request so the follower tracks the leader's output in hardware — no second control loop, no RIO involvement. You never see the follower again; it's not even a field.

5Four-bar · control mode

.controlMode(...)
.controlMode(ControlMode.VOLTAGE)   // ported v1 volts gains; FOC after SysId
🧠 Why VOLTAGE and not the FOC default?

The gains were ported from v1's voltage-based software PID, so they're in volts-per-unit. TorqueCurrentFOC gains are amps-per-unit — a completely different number. Running FOC with voltage gains would be wrong and possibly violent. So the migration ships on VOLTAGE (correct today) and the comment marks the upgrade path: run SysId, get amp-based gains, flip this one field to TORQUE_CURRENT_FOC. The library keeps both request families pre-allocated, so it really is a one-word change.

💡 Simulation ignores this

In sim the archetype forces VOLTAGE regardless — it's the best-supported sim path — and uses the sim gain set. So this field only matters on the real robot.

6Four-bar · ratio & gains

ratio + gains
.rotorToMechanismRatio(GEARING)          // 14.14 rotor turns per four-bar turn
.gains(FOUR_BAR_GAINS, FOUR_BAR_SIM_GAINS)

The ratio

rotorToMechanismRatio(14.14) is what makes "command in radians" possible. It's written into the device's SensorToMechanismRatio, so the TalonFX itself reports and accepts mechanism position. Everything downstream — soft limits, MotionMagic, setGoal — is in four-bar radians, never rotor ticks.

⚠️ No fused CANcoder here — yet

There is an absolute encoder on the robot (id 12), but it isn't fused yet (that needs an on-robot offset calibration — a flagged follow-up). So the four-bar uses rotor-only feedback and is seeded at boot in the constructor (§11). Fusing it later is a two-line change: swap .rotorToMechanismRatio(...) for .fusedCANcoder(...) and drop the seed.

The gains

Two sets, real and sim. The real set is new Gains(4π, 0, 0).withGravity(0.8, Arm_Cosine) — proportional only, plus gravity. Arm_Cosine means the device scales the 0.8 kG by cos(angle), so it fights gravity hardest when the four-bar is horizontal and not at all when vertical — which requires the mechanism zero to be horizontal (it is, by the geometry convention in the constants).

7Four-bar · motion profile & peak voltage

.motion(...) + .peakVoltage(...)
.motion(FOUR_BAR_MOTION)                              // trapezoid, cruise ≈ 1.5 rad/s
.peakVoltage(FOUR_BAR_PEAK_VOLTS, -FOUR_BAR_PEAK_VOLTS)   // ±1.5 V hard clamp
🧠 Why two speed limits, and why trapezoid not Expo?

v1 limited the four-bar's speed in two independent ways: a velocity clamp (±1.5 rad/s) and an output-voltage clamp (±1.5 V). The migration preserves both exactly:

  • Trapezoidal MotionConstraints(1.5 rad/s, 2.0, 0) reproduces the velocity clamp — a fixed cruise speed is exactly what a trapezoid gives you. Expo (the usual default) wouldn't reproduce that specific 1.5 rad/s cap.
  • peakVoltage(±1.5) reproduces the output clamp — a second, independent ceiling. Belt-and-suspenders, intentionally, because that's how the mechanism was validated in competition.

This is "refactor, not redesign" in action: the behavior is bit-for-bit the old one, just expressed declaratively.

8Four-bar · soft limits · current budget · tolerance

safety & readiness
.softLimits(Radians.of(INTAKE_MIN_ANGLE_RAD), Radians.of(INTAKE_MAX_ANGLE_RAD))  // 0 … 2.4 rad
.currentBudget(FOUR_BAR_BUDGET)                                                   // 80 A stator / 60 A supply
.tolerance(Radians.of(INTAKE_ANGLE_TOLERANCE_RAD))                               // 0.003 rad
LineWhat · why · what breaks without it
.softLimits(0, 2.4)Device-enforced travel range. Goals are clamped before being commanded, and the TalonFX won't drive past them even under a bug. Without it, a bad setpoint could slam the four-bar into a hard stop at full current.
.currentBudget(80, 60)80 A stator (torque/heat ceiling), 60 A supply (breaker protection). Enough to move a two-motor four-bar briskly; low enough not to trip the main breaker or cook the motors.
.tolerance(0.003)Defines when "at goal" is true — used by atPositionTrigger (§11). 0.003 rad ≈ 0.17°, tight because the superstructure gates on it. Too loose → the robot thinks the intake is placed when it isn't.

9Four-bar · neutral mode & the sim model

.neutralMode(...) + .simArmModel(...)
.neutralMode(Coast)
.simArmModel(DCMotor.getKrakenX60Foc(2), GEARING, 0.3, 0.3,
             INTAKE_MIN_ANGLE_RAD, INTAKE_MAX_ANGLE_RAD, START_ANGLE_RAD));
🧠 Why Coast, not Brake?

A four-bar you want to be able to back-drive by hand — to stow it in the pit, or to hand-zero it. Brake mode would fight you. Coast also means that on disable the mechanism goes limp instead of locking. (The library additionally forces all mechanisms to a safe state on disable regardless.) Coast here is a static import of NeutralModeValue.Coast.

💡 The sim model = the one line that makes it move in simulation

simArmModel(2 Krakens, gearing, MOI≈0.3, length≈0.3, min, max, start) attaches a WPILib SingleJointedArmSim, fed by the TalonFX's simulated output voltage and feeding rotor position back. Drop this line and the four-bar simply won't move in simulateJava — the control logic runs, but there's no physics for it to act on. The MOI/length are rough estimates; sim exists to exercise logic, not to be exact.

10The roller — why it's four lines

the roller
private final RollerMechanism roller = new RollerMechanism(
        new MechanismConfig("Intake/Roller", new CANDeviceId(ROLLER_MOTOR_ID))
                .controlMode(ControlMode.VOLTAGE)
                .currentBudget(ROLLER_BUDGET)
                .simRotationalModel(DCMotor.getKrakenX60Foc(1), 0.002, 3.0));
🧠 Why so much less config than the four-bar?

A roller is open-loop — it doesn't hold a position or a speed, it just spins. So it has no gains (nothing to close), no motion profile (nothing to profile), no soft limits (it spins freely), no tolerance (no target). The archetype's job here is small: send a duty-cycle / voltage / current output, and offer a current-spike detector for game-piece detection. Fewer knobs because there's genuinely less to decide.

💡 The one thing it still gets for free

Even this minimal roller gets verified config, batched status signals, DogLog telemetry, a debounced disconnect alert, and a sim model — the same infrastructure the four-bar gets. The RollerMechanism also exposes currentSpike(amps, seconds) for "a game piece stalled the roller," though this intake doesn't use it here.

11The constructor — seeding & the state machine

fourBar.resetPosition(...)

seed the position
fourBar.resetPosition(Radians.of(START_ANGLE_RAD));   // START ≈ π − 0.7326 − 0.159
🧠 What is that magic angle, and why seed at all?

Because the CANcoder isn't fused yet (§6), the four-bar's position is relative — it only knows how far it's turned since boot. At power-on the mechanism is physically stowed, so we tell it "you are at the stow angle now." The exact value π − 0.732601 − 0.159 is the empirically-measured stow angle carried over verbatim from v1 (the arithmetic is left un-collapsed so the calibration history stays legible). Skip this and every angle would be offset by wherever the rotor happened to boot.

The state machine

the machine
machine = new StateMachine<>("Intake", CLOSE)
        .whileIn(OPEN,  run(() -> { fourBar.setGoal(Radians.of(OPEN.angle));  roller.runDutyCycle(OPEN.voltage); }))
        .whileIn(CLOSE, run(() -> { fourBar.setGoal(Radians.of(CLOSE.angle)); roller.runDutyCycle(CLOSE.voltage); }))
        .whileIn(PUMP,  pumpCommand())
        .transitionFromAny(OPEN)
        .transitionFromAny(CLOSE)
        .transitionFromAny(PUMP);
🧠 Why whileIn and not onEnter?

onEnter fires once. whileIn schedules a command that runs the whole time the machine is in that state. The intake wants the latter: as long as it's OPEN, keep commanding the four-bar's goal and keep the roller spinning, every loop. If it were onEnter, a single setGoal would fire and then nothing would keep the roller running.

🧠 Why run(...)?

run(...) is SubsystemBase.run — it builds a RunCommand that executes the lambda every loop and takes this subsystem as a requirement. The requirement matters: it means only one intake command runs at a time, and the state machine's command is properly interruptible by the command scheduler. Using a bare lambda without run would lose the requirement and the scheduling semantics.

💡 transitionFromAny on every state = "any state reachable from anywhere"

The intake has no illegal orderings — you can go CLOSE→PUMP, OPEN→CLOSE, whatever. Declaring transitionFromAny for all three states says exactly that. A mechanism with real interlocks (e.g. "can't extend while climbing") would instead declare only the specific legal edges, and the un-declared ones would be denied. Here, freedom is intentional and explicit — not an accident of omission.

atPositionTrigger

the readiness trigger
atPositionTrigger = new Trigger(() -> Math.abs(
        machine.getCurrentState().angle - fourBar.getPosition().in(Radians)) < INTAKE_ANGLE_TOLERANCE_RAD);

A Trigger that's true when the four-bar is within tolerance of the current state's target angle. The superstructure reads this to know the intake is placed before it acts. It compares against machine.getCurrentState().angle rather than a fixed value, so it automatically tracks whatever state the intake is in — one trigger, correct in every state.

12The pump command

pumpCommand()
private Command pumpCommand() {
    return Commands.repeatingSequence(
            run(() -> { fourBar.setGoal(Radians.of(PUMP_HIGH_ANGLE_RAD)); roller.runDutyCycle(PUMP.voltage); }).withTimeout(0.5),
            run(() -> { fourBar.setGoal(Radians.of(PUMP_LOW_ANGLE_RAD));  roller.runDutyCycle(PUMP.voltage); }).withTimeout(0.5))
        .withName("Intake Pump");
}
🧠 What is "pumping" and why build it this way?

PUMP oscillates the four-bar between a high (1.6 rad) and low (0 rad) angle every half second while the roller keeps feeding — a physical "shake" to unjam / seat game pieces, carried over from v1. It's expressed as command composition:

  • run(...).withTimeout(0.5) — command the high angle for half a second,
  • a second run(...).withTimeout(0.5) — then the low angle for half a second,
  • Commands.repeatingSequence(...) — do the two forever, alternating.

This is why the machine uses whileIn(PUMP, pumpCommand()): the whole repeating sequence runs as long as PUMP is active and is cancelled the instant the state changes. No timers, no flags, no manual state — the command framework is the timing engine.

13The public API — three deliberate methods

public surface
public Command setStateCommand(IntakeStates state) { return machine.requestCommand(state); }
public void requestState(IntakeStates state)       { machine.request(state); }
public Command coastCommand()                      { return fourBar.coastCommand(this); }
MethodFor whom · why it exists
setStateCommand(s)For bindings & autos — returns a Command you can put on a button or in a PathPlanner named command. Requesting a state is a schedulable action.
requestState(s)For the superstructure's fan-out — a plain, immediate call (no Command wrapper) because the superstructure's own state machine drives it from an onEnter and doesn't want a nested command.
coastCommand()For the pit crew — hold it to let the four-bar go limp so you can move it by hand. Runs while disabled (the archetype's coast command ignores the disabled state).
🧠 Why two ways to request a state?

The same intent, two call styles, because the two callers are different. A button wants a Command (scheduled, interruptible). The superstructure is already inside a state-machine callback and wants a direct, synchronous poke. Offering both keeps each caller clean instead of forcing one to adapt to the other.

14periodic() — the three lines you must not forget

periodic()
@Override public void periodic() {
    fourBar.periodic();
    roller.periodic();
    machine.periodic();
}
🚫 This is the #1 thing people forget

Each mechanism's periodic() does its telemetry, its disconnect-alert debounce, and — critically — its simulation step. The machine's periodic() ticks pending transitions and logs state. Miss any of these calls and that piece silently goes dark: no logs, no sim motion, no state progress. There's no error — it just doesn't work. Three lines, non-negotiable.

💡 Order doesn't matter here (but it can)

These three are independent, so their order is free. In a subsystem where a mechanism's reading feeds a decision within the same loop, you'd order deliberately. And globally, SignalHub.refreshAll() in Robot.robotPeriodic has already made every sensor value fresh before any subsystem periodic() runs.

16The same intake in v1 — for contrast

The pre-migration Intake did all of the above by hand. A few representative differences:

✅ Same robot behavior, a fraction of the surface area

The migration preserved the intake's competition behavior exactly (angles, pump timing, the two speed clamps, boot seeding) while deleting the hand-written control, unit, follower, state, sim, and telemetry plumbing. What's left is the file you just read — and every line of it now has a reason you can point to.
